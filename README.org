This manual describes the features and customization options for the Emacs Lisp package =agent.el=.

When you start a Claude or Codex session from a registered Elpaca build tree,
Agent uses that package’s source checkout. Elpaca can replace build directories
during a rebuild, which invalidates a running process’s working directory. This
applies to explicit session directories and directories inferred from the current
buffer. Other directories retain their usual behavior. A missing registered source
directory prevents the session from starting.

* Overview
:PROPERTIES:
:CUSTOM_ID: h:overview
:END:

=agent.el= collects the Emacs integration layer for AI coding command-line tools. It provides a shared session model, a unified transient menu, notification handling, terminal helpers, backend modules for Claude Code and Codex, and an optional chief-of-staff loop.

The package is split into a small backend-agnostic core and focused modules:

| Module               | Role                                                                                                                                                                                                                        |
|----------------------+-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| =agent.el=           | Core: backend registry, session identity and state machine, session keys and teardown, unified orchestration commands (handoff, restart, exit, resume, branch navigation, skills, audits, backtrace debugging), transient menu, alerts, theme sync |
| =agent-account.el=   | Multi-account support shared by all backends: selection, persistence, per-account config homes, symlinked shared state                                                                                                      |
| =agent-usage.el=     | Per-account usage store and poller shared by all backends                                                                                                                                                                   |
| =agent-capture.el=   | Persisted Org prompt capture, keyed to the session it targets                                                                                                                                                               |
| =agent-project.el=   | Account-scoped project sources: registry and path-pattern candidates, model ranking, and the project prompt for things that carry no directory of their own                                                                 |
| =agent-slack.el=     | Slack-message-to-project routing: reads the message at point as text with no directory of its own, leaving the project to the shared project reader                                                                          |
| =agent-forge.el=     | Forge-notification-to-project routing: starts a session in the working tree of the repository the notification belongs to                                                                                                   |
| =agent-mu4e.el=      | Email-to-project routing: reads the mu4e message at point as a maildir path, leaving the project to the shared project reader                                                                                                |
| =agent-snippet.el=   | Yasnippet TAB expansion and snippet insertion in eat-based session buffers                                                                                                                                                  |
| =agent-todo.el=      | Org TODO workflows that work with any backend: batch processing of a list of entries and routing the entry at point to a session                                                                                             |
| =agent-claude.el=    | Claude Code backend: integrates =claude-code.el= with status and usage polling, hook setup, and ~agent-claude-mode~                                                                                                          |
| =agent-claude-cli.el= | Quarantined undocumented Claude CLI conventions: Keychain credential naming, the usage API endpoint, the =~/.claude/projects/= directory encoding, transcript JSONL parsing, and the =.claude.json= merge engine            |
| =agent-codex.el=     | Codex backend: integrates =codex.el= with theme sync, =codex exec= execution, =config.toml= helpers, modeline helpers, and ~agent-codex-mode~                                                                               |
| =agent-chief.el=     | Inspectable chief-of-staff loop: Emacs owns timers, state, context collection, and notifications, while Claude Code or Codex provides one-shot judgment on each tick                                                        |

The main workflow is to load =agent.el=, require the backend modules you use, and enable their minor modes (see [[#h:minor-modes][Backend minor modes]]); loading a backend module installs nothing by itself. Once the Claude and Codex modules are active, =M-x agent-menu= and =M-x agent-select-session= operate across both tools. Sessions are listed with their account in a column of its own, highlighted when waiting for input, and disambiguated by project and instance name when several sessions share a directory.

The package depends on =transient= for menus, =consult= for completion, =claude-code.el= for the Claude backend, and =codex.el= for the Codex backend. All four are declared in the package metadata so that the package manager builds =agent= with them available; the backend modules hard-require their respective backend at load time. Optional integrations use packages such as =yasnippet=, =doom-modeline=, =gptel=, =agent-log=, and =monet= when those are available.

* Architecture
:PROPERTIES:
:CUSTOM_ID: h:architecture

** Session identity
:PROPERTIES:
:CUSTOM_ID: h:session-identity
:END:

#+findex: agent-session
#+findex: agent-session-buffer-name
Every live session buffer carries a buffer-local ~agent-session~ struct, captured once when the session starts. Its slots are ~backend~ (the backend symbol), ~account~ (the account name, or nil for the default), ~directory~ (the abbreviated project directory), ~instance~ (the instance name, or nil), and ~id~ (the CLI session id, or nil until known). The function ~agent-session~ returns the struct for a buffer, and ~agent-session-buffer-name~ derives the canonical buffer name from the identity. All orchestration code reads identity from this struct; nothing parses buffer names.

#+findex: agent-session-buffers
#+vindex: agent-session-id-functions
The ~id~ slot holds the backend's native session id and is maintained for the whole session lifetime: a non-fork resume seeds it in ~agent-start-session~, the Claude backend records the ~session_id~ reported by every status poll (so a branch switch, which changes the id, updates it), and the Codex backend records the id ~codex-session-identity~ reports on every CLI hook event. A fresh session therefore acquires its id within one status poll interval (Claude) or at its first hook event or prompt submission, whichever comes first (Codex); a fresh app-server Codex session knows its thread id before any CLI hook event fires, so the submission hook is the earliest per-buffer signal. Whenever the recorded id changes, the abnormal hook ~agent-session-id-functions~ runs with the session buffer, so optional integrations — such as the Agent Log bridge — can observe identity without reading private variables. The public surface for such integrations is ~agent-session~, the ~agent-session-id~ accessor, ~agent-session-buffers~ (all live session buffers across backends), and ~agent-session-display-state~.

** Session state machine
:PROPERTIES:
:CUSTOM_ID: h:session-state-machine
:END:

#+findex: agent-session-event
Each session buffer tracks its readiness in the buffer-local variable ~agent--session-state~, which is one of ~unknown~, ~busy~, ~awaiting-input~, or ~closing~. Buffers start as ~unknown~ and stay there until a session event arrives, so a state that was never observed is never presented as one that was; the session switcher renders such sessions with ~agent-unknown~ and ~agent-jump-to-waiting~ skips them. All transitions go through ~agent-session-event~, which accepts the events ~stop~, ~idle-prompt~, ~blocked~, ~submit~, ~activity~, and ~exit-request~. An ~activity~ event marks the session busy on evidence that it is working. It exists because turns the user did not type in Emacs — one driven by remote control, a scheduled task, or a resumed background job — would otherwise be unobservable, leaving the session displayed as waiting while it works. Claude Code has no busy/idle state of its own, so the backend assembles one from its hooks. The bundled =notify-emacs-state.sh= wrapper forwards the =UserPromptSubmit=, =PreToolUse=, =PostToolUse=, =PostToolUseFailure=, and =SubagentStart= hooks as ~activity~, whoever started the turn, and =StopFailure= — a turn ended by an API error, which fires no =Stop= hook — as ~stop~. The tool hooks also return a session to busy once the user answers a permission dialog. Because these hooks fire on every tool call of every session and subagent, most of them report a session Emacs already marks busy. To keep that traffic off the Emacs server, ~agent-claude--record-state~ mirrors each Claude session's state to a file in ~agent-claude-status-directory~, keyed by the session's per-process UUID like its statusline file, and the wrapper skips an ~activity~ event while that file reads =busy=. A missing or unreadable file sends the event as before, and a failed write deletes the file. Other backends can observe transitions through ~agent-session-state-change-functions~. Each forwarded event carries its send time, and ~agent-claude--stale-hook-event-p~ discards one sent before the session last began waiting, because background delivery can land a turn's final tool event after its stop event. A turn Claude starts without a prompt and runs without tools fires none of these hooks, so the status-line poll remains as a fallback: Claude's status line reports a fresh ~prompt_id~ for every turn whatever its origin, and ~agent-claude--detect-turn-start~ emits ~activity~ when the identifier changes, within one poll interval, ~agent-claude-status-interval~. A turn shorter than that interval both begins and ends between polls, and its ~stop~ event has already landed by the time the change is seen, so that case is detected and skipped rather than stranding the session as busy. Interrupting a turn fires no hook at all, so an escape sent with ~claude-code-send-escape~ to a busy session schedules ~agent-claude--check-interrupt~: after ~agent-claude-interrupt-check-delay~ seconds, if the session is still busy with no state change since the escape and its terminal shows the idle input prompt, the session is marked ~blocked~. An interrupt from outside Emacs, such as through remote control, is not detected until the next turn ends. A ~blocked~ event marks the session as waiting on the user without firing a ready alert, and is used for permission and elicitation dialogs: Claude reaches those from inside a turn with a tool call still in flight, so nothing else reports them as waiting even though they proceed only once the user answers. Backends translate raw CLI notifications into these events and never set session state directly. A ~stop~ or ~idle-prompt~ event first offers the transition to the before-exit chain; when the chain consumes it, ready alerts and display refreshes are suppressed. Ready alerts fire only for ~idle-prompt~ events, and a ~submit~ event delivered while the session is already busy is ignored, because backend submission hooks can fire more than once per submission.

** Session teardown and leak policy
:PROPERTIES:
:CUSTOM_ID: h:session-teardown
:END:

Session resource cleanup has a single owner: ~agent--session-teardown~ runs a session buffer's ~agent--teardown-functions~ exactly once, whether the buffer is killed first or the CLI process exits first. Backends and features register their per-session resources (status poll timers, monet servers, before-exit chains) as teardown functions instead of installing their own kill-buffer hooks. A session key has buffer lifetime instead: assigning one atomically installs its buffer-kill cleanup, while session teardown can release it early after process exit. Claude buffers also adopt any already-running Monet server when ~agent-claude-mode~ is enabled or reloaded. The monet websocket server needs one extra guard: when the Claude client disconnects, ~monet--on-close-server~ drops the session from monet's own table before teardown can look it up, so an =:after= advice closes the listening server at that moment rather than letting it escape to the GC safety net. Resources that escape teardown are not silently reaped: safety nets report each one through a =Warnings= buffer entry tagged =agent=, naming the leaked resource. A leak warning therefore indicates a lifecycle bug worth reporting, not routine noise. The Monet GC sweep identifies servers by ownership, not by process name: Agent registers every server process it sees monet create or adopt, and the sweep only ever reaps registered servers that have lost their monet session. Websocket servers belonging to other packages (atomic-chrome, org-roam-ui) share the generic =websocket server on port N= process name but are invisible to the sweep and can never be reported or killed as monet leaks.

** Account model
:PROPERTIES:
:CUSTOM_ID: h:account-model
:END:

#+findex: agent-account-select
#+findex: agent-account-init
Multi-account state lives in =agent-account.el= and is keyed by backend. Each backend declares an accounts alist mapping account names to per-account configuration homes (~agent-claude-accounts~, ~agent-codex-accounts~), a persisted selection file that survives Emacs restarts (~agent-claude-account-file~, ~agent-codex-account-file~), and the environment variable that points the CLI at the selected home: =CLAUDE_CONFIG_DIR= for Claude Code and =CODEX_HOME= for Codex. Account homes keep credentials separate, while shared state (settings, hooks, skills, sessions, history) is symlinked from the backend's canonical home so it remains available after switching accounts; conflicting account-local files are backed up to timestamped =*.agent-backup-*= siblings first. Codex hook trust is keyed by the lexical =hooks.json= path rather than the symlink target, so account sync copies the canonical path's persisted trust state to the account path. It copies existing hashes rather than computing new ones; a changed canonical hook therefore remains untrusted. Any sync failure aborts session startup instead of letting a session run with missing or stale policy. ~agent-account-select~ persists a choice and syncs the account home, and ~agent-account-init~ prepares or repairs a home. The account infix in ~agent-menu~ always asks which backend to change before it asks for an account; it never silently infers the backend from the buffer where the menu happened to be opened. When the merge engine reads a home's =.claude.json=, a parse failure is retried over increasing delays before warning, since a running CLI rewrites the file frequently and a read can land mid-write; a failure that persists is warned about once, with the invalid bytes preserved in a snapshot file so a torn read can be told apart from real corruption. Writes go to a temporary file that is renamed into place, so concurrent readers never observe a truncated =.claude.json=. The account a session was started under is recorded in its ~agent-session~ struct, so restart and handoff preserve it even after the global selection changes.

#+findex: agent-account-property
#+findex: agent-account-route
An accounts entry is either =(NAME . HOME)= or =(NAME :home HOME :pool POOL ...)=. The plist form carries arbitrary further properties, read with ~agent-account-property~, for integrations that need per-account settings beyond the home. Accounts sharing a ~:pool~ are interchangeable: they hold the same configuration and differ only in whose quota they spend. The selection prompt lists pools ahead of accounts, and selecting a pool persists the pool name, so ~agent-account-current~ may answer with a pool; ~agent-account-resolve~ always answers with a concrete account, routing a pool selection through ~agent-account-route~. Selecting a pool syncs every member's home, so routing never has to touch the filesystem. A member chosen by name pins that account as before. A pool may carry the same name as one of its members — convenient when an existing selection file names the first of what became several equivalent accounts — in which case the name is listed once and selects the pool, so that member can no longer be pinned by name.

#+vindex: agent-account-route-hysteresis
#+findex: agent-account-usage-score
Routing skips members whose credentials are missing, then sets aside members whose latest fresh usage reading ([[#h:usage][Account usage]]) flags them as limited or shows either window at 100%. The rest are ranked by ~agent-account-usage-score~: the larger of the weekly and session percentages, with the weekly share breaking ties, so lower is better; a member with no fresh reading ranks after every member with one. The member the pool was last routed to is kept unless a sibling beats it by ~agent-account-route-hysteresis~ points (default =10=), so near-equal members do not alternate between consecutive sessions — except that a current member with unknown usage never holds off a sibling with a known score. When every member is limited, the one whose window resets soonest is returned, and the echo area says so, so the session start can still report the limit. A route that changes hands is announced with the chosen member's usage; a resolution that keeps the previous member stays silent, since routing also runs for background processes and would otherwise flood the echo area. Every routing decision is followed by a refresh of the pool's readings. A restart of a session whose account belongs to the selected pool reruns routing without prompting, so an exhausted member can be replaced by one with capacity. Both backends share session history between account homes, so the conversation is preserved.

#+findex: agent-account-login
Credentials are part of the account model too. A backend may declare the account-local credentials file inside each home (=auth.json= for Codex) and the CLI arguments of its login flow. ~agent-account-login~ — bound to =a l= in ~agent-menu~ — runs that login flow with the selected account's environment, so the credentials always land in the right account home; running the bare CLI login in a terminal would write to the backend's default home instead. The command shows the login output, including the authentication URL, in a dedicated buffer and reports success or failure when the flow finishes. Session starts guard on the same declaration: when an account's credentials file is missing — after the in-session logout command, or when tokens were removed out of band — ~agent-start-session~ refuses to spawn a session that could only fail to authenticate and points at ~agent-account-login~ instead. Backends that do not declare a credentials file (Claude Code stores credentials in the macOS Keychain) are assumed logged in and never blocked.

** Account usage
:PROPERTIES:
:CUSTOM_ID: h:usage
:END:
#+vindex: agent-usage-interval
#+vindex: agent-usage-max-interval
#+vindex: agent-usage-cache-file
#+vindex: agent-usage-stale-after
#+findex: agent-usage-get
#+findex: agent-usage-fetch
Per-account usage lives in =agent-usage.el= and is keyed by backend and account. A backend that can report usage declares a ~:usage-fetch~ slot: a function called with an account name and a callback, which it calls with a normalized plist or nil. The plist carries ~:session-pct~ and ~:weekly-pct~ (percent of the short and long windows used), ~:session-reset~ and ~:weekly-reset~ (reset times as float seconds), ~:limited~ (non-nil when the backend refuses further requests), and ~:fetched-at~. Claude reads the undocumented =api/oauth/usage= endpoint with the Keychain OAuth token; Codex reads the ChatGPT =wham/usage= endpoint with the access token and account id stored in the account home's =auth.json=, classifying a window of at least a day as weekly and a shorter one as the session window, so a plan with a single weekly window reports only that. ~agent-usage-get~ answers the latest reading and ~agent-usage-fetch~ refreshes one account.

One poller serves every backend. It starts with the first session of any backend and stops when the last one is torn down, polling every account that has a live session plus every member of every pool, so routing has data for idle members too. ~agent-usage-interval~ defaults to =300= seconds and doubles after a failed fetch up to ~agent-usage-max-interval~, which defaults to =900=; a success resets it. Readings are written to ~agent-usage-cache-file~ after every fetch and read back on first use, so a fresh Emacs can route before its first poll completes; a reading older than ~agent-usage-stale-after~ seconds no longer counts for routing. The Claude status helpers ~agent-claude-status-session-usage~ and friends read this store and keep answering ISO timestamps for the reset times. Claude usage requests report synchronous network failures, including DNS lookup errors, as failed fetches without entering the debugger. Only stale URL process write failures are retried immediately, once.

#+findex: agent-usage-show
~agent-usage-show~ — bound to =a u= in ~agent-menu~ — lists every configured account, live-session account, and pool member in a =*agent-usage*= buffer with its pool, session and weekly percentages, weekly reset time, limit flag, and the age of the reading, then fetches fresh readings and re-renders as each arrives; =g= refreshes again. Configured accounts appear even without a live session; backends without configured or active accounts show their default account. Background polling remains limited to live-session accounts and pool members. The limit flag and the percentages are what routing acts on, so the buffer shows at a glance why a pool went to the member it did.

** Backend minor modes
:PROPERTIES:
:CUSTOM_ID: h:minor-modes
:END:

#+findex: agent-claude-mode
#+findex: agent-codex-mode
The global minor modes ~agent-claude-mode~ and ~agent-codex-mode~ own every hook, advice, timer, and notification handler their backend installs. Loading =agent-claude.el= or =agent-codex.el= installs nothing; the modes must be enabled explicitly. Disabling a mode removes its hooks and advice symmetrically and restores the backend's previous notification function, leaving running sessions untouched. A typical setup:

#+begin_src emacs-lisp
(use-package agent
  :config
  (require 'agent-claude)
  (require 'agent-codex)
  (require 'agent-chief)
  (agent-claude-mode 1)
  (agent-codex-mode 1))
#+end_src

** Shared session behavior
:PROPERTIES:
:CUSTOM_ID: h:shared-session-options
:END:

#+vindex: agent-protect-buffers
#+vindex: agent-warn-kill-with-branches
#+vindex: agent-branch-worktree-directory
#+vindex: agent-alert-on-ready
#+vindex: agent-alert-style
#+vindex: agent-alert-sound
#+vindex: agent-alert-sound-player
#+vindex: agent-backtrace-file
#+vindex: agent-handoff-files
#+vindex: agent-audit-skills
#+vindex: agent-audit-project-directories
#+vindex: agent-debug-backtrace-model
#+vindex: agent-debug-backtrace-backend
#+vindex: agent-prompt-capture-directory
#+vindex: agent-prompt-capture-auto-save-delay
#+vindex: agent-sync-theme
#+vindex: agent-sigwinch-delay
#+vindex: agent-session-annotation-max-width
The user option ~agent-protect-buffers~ is a boolean that defaults to ~t~. When enabled, killing a live AI session buffer prompts for confirmation through ~agent-protect-buffer~. Buffers whose processes have already exited are allowed to die without the prompt.

The user option ~agent-warn-kill-with-branches~ is a boolean that defaults to ~t~. When enabled, killing a session that other sessions were branched from asks a second confirmation naming how many branches it has, after the ordinary kill-protection prompt. The check scans only the sessions that could descend from the one being killed, and any failure to scan allows the kill, so a session never becomes unkillable because its transcripts moved. It replaces ~agent-claude-warn-kill-with-branches~, which is kept as an obsolete alias; that option was declared but never read by any code, so setting it had no effect until the check described here existed.

The user option ~agent-branch-worktree-directory~ names the base directory for the git worktrees ~agent-create-branch~ creates with a prefix argument ([[#h:branch-navigation][Branch navigation]]). It defaults to a location under the cache directory, away from cloud sync, and replaces ~agent-claude-fork-worktree-directory~, which is kept as an obsolete alias. The default path still ends in the literal segment =claude-worktrees=, unchanged from the Claude-only original so that worktrees created before the rename are still found where they were left.

The user option ~agent-alert-on-ready~ is a boolean that defaults to ~nil~. When enabled, backend notification handlers can call ~agent-notify~ to emit visual and/or audible alerts when a session is waiting for input. Codex's own terminal-bell notification path is routed through the same alert setting. Visual alerts preserve the current echo-area message even when the selected =alert.el= style runs a synchronous notifier process. ~agent-alert-style~ selects ~visual~, ~sound~, or ~both~; it defaults to ~both~. ~agent-alert-sound~ defaults to ~nil~; set it to a sound file to enable sound alerts. ~agent-alert-sound-player~ optionally names an external sound player when Emacs sound support is unavailable.

The user option ~agent-backtrace-file~ controls where ~agent-save-backtrace~ and ~agent-debug-backtrace~ write Emacs backtraces. It defaults to a file in ~temporary-file-directory~.

The unified orchestration commands share one set of options across backends. ~agent-handoff-files~ maps backend symbols to the handoff files read by ~agent-handoff~. ~agent-audit-skills~ lists the audit skills run by ~agent-audit-project~, and ~agent-audit-project-directories~ stores completion candidates for the audit directory prompt. ~agent-debug-backtrace-model~ and ~agent-debug-backtrace-backend~ configure the =gptel= request used by ~agent-debug-backtrace~ to identify likely culprit packages from an Emacs backtrace.

Slack-message routing has no options of its own any more. The model and =gptel= backend that pick a project from the message are the shared ~agent-project-ranking-model~ and ~agent-project-ranking-backend~ ([[#h:project-options][Project sources]]), and ~agent-act-on-slack-message-model~ and ~agent-act-on-slack-message-backend~ are obsolete aliases of them. The project candidates come from ~agent-project-sources~, so a registry that used to be named by ~agent-epoch-project-registry-file~ now belongs in that alist: that option is obsolete and nothing reads it, which means a configuration setting it alone routes against the default source list instead of the registry. Loading =agent-project= warns when that option still holds a value, because marking a variable obsolete warns only code that mentions it and says nothing to a configuration that merely sets it, which is the whole of what such a configuration does. ~agent-epoch-projects-root~ is an obsolete alias of ~agent-project-registry-root~ and still resolves the registry's relative paths. The function ~agent-epoch-project-candidates~, which read that registry into project plists, is replaced by ~agent-project-candidates~, which reads every source an account has and answers in a different shape. The old name is marked obsolete but no longer defined, so a configuration still calling it is warned at byte-compile time which name replaced it, and fails if it runs. All three renamings are declared in =agent-project.el= ahead of the options they rename, because a setting made before the package loads — which is what ~use-package~'s ~:custom~ does — reaches the new name only while that name is still unbound.

The user option ~agent-prompt-capture-directory~ controls where ~agent-capture-prompt~ stores per-session Org files. Each file is keyed by backend, account, project directory, and session instance, so prompts are linked to the session they target and remain available after Emacs restarts. ~agent-prompt-capture-auto-save-delay~ controls the idle delay before capture buffers are saved automatically.

The user option ~agent-sync-theme~ is a boolean that defaults to ~nil~. When enabled, theme changes in Emacs are persisted through each registered backend's theme-sync handler. This updates configuration files for new or restarted CLI sessions without sending theme commands into active terminal conversations.

The user option ~agent-sigwinch-delay~ is a number of seconds and defaults to =0.5=. It controls how long ~agent-fix-rendering~ waits before sending =SIGWINCH= to a terminal process. Increase it if an AI CLI reads the terminal size before the =eat= window has settled.

The user option ~agent-session-annotation-max-width~ caps the width of session annotations in the session switcher ([[#h:shared-commands][Shared commands]]). It defaults to ~nil~, which applies no cap beyond the fit to the frame. An integer narrows annotations to at most that many columns; it never widens them past what the frame holds, since the frame fit applies either way. Text longer than the resulting width is truncated with an ellipsis. A cap of =0= leaves no room at all, and every session then renders as the bare label it would have without an annotation, rather than a padded label followed by nothing.

Snippet helpers use =yasnippet= and =consult-yasnippet= only when those optional packages are loaded.

** Project sources
:PROPERTIES:
:CUSTOM_ID: h:project-options
:END:

#+vindex: agent-project-sources
#+vindex: agent-project-registry-root
#+vindex: agent-project-ranking-model
#+vindex: agent-project-ranking-backend
#+findex: agent-project-candidates
#+findex: agent-project-read
The =agent-project= module enumerates the projects a session can be started in when the thing the session acts on carries no directory of its own. The user option ~agent-project-sources~ is an alist of (REGEXP . SOURCES). The regexp is searched for anywhere in the account name of the backend that will run the session — anchor it with =\`= and =\'= to match a whole name, since a bare ="epoch"= also matches an account called =epoch-personal= — and the first matching entry wins, so an empty regexp is a catch-all that also covers a backend with no account selected. It defaults to one catch-all entry listing =~/repos/*=.

Each source is either a registry file, whose name ends in =.json=, or a path pattern.

A path pattern may contain wildcards. A wildcard is =*=, =?=, or a =[...]= character class, and a pattern containing one is expanded a single level per wildcard component: =~/repos/*= reaches the children of =~/repos/=, and =~/repos/.worktrees/*/*= its grandchildren two levels down. Wildcard expansion keeps only git repositories and worktrees; a worktree records its git directory in a file rather than a directory, and both count. A pattern without a wildcard names exactly one directory, which is kept whether or not it is a repository, and dropped when it does not exist or is not a directory. A pattern that cannot be expanded at all, such as one holding an unbalanced =[=, is reported in the echo area and skipped, so one malformed source never suppresses the candidates of the others.

A registry is a JSON file holding a =projects= array, in the format the obsolete ~agent-epoch-project-registry-file~ used to read ([[#h:shared-session-options][Shared session behavior]]). Every entry becomes one candidate, labelled by its =id= and =title=, or by its =id= alone when it records no title. Unlike a path pattern it carries a description: the entry's =summary=, or its =aliases= when it records no summary, followed by its =browser_keywords= and its Slack channels; an entry recording none of the four has no description at all rather than an empty one. The keywords are worth their length: they are the terms the project is recognized by elsewhere, repository slugs and domain names among them, which is what a routed Slack message or email is likeliest to name, whereas aliases are often the title restated. An entry that records a JSON =null= where a string belongs counts as recording nothing, so a null summary falls back to the aliases just as an omitted one does. Later stages use that text to judge which project a piece of text is about. An entry's directory is its first =project_doc_paths= folder when it records one, because that folder holds the project's instruction files, its first =repo_paths= directory when it records only that, and the registry root itself when it records neither. The user option ~agent-project-registry-root~ names the directory those relative paths are expanded against; it defaults to ~nil~, and a registry recording relative paths is unusable until it is set. A source naming a registry that does not exist raises an error rather than being skipped, since it points at a file the user meant to have.

The function ~agent-project-candidates~ returns the candidates for an account as plists with ~:label~, ~:directory~, ~:repository~ and ~:description~. The repository is the candidate's local clone: the directory itself for a path source that is a git repository or worktree, the first =repo_paths= directory for a registry entry, and nil for a project holding no clone of its own. It is what ~agent-project-repository-directory~ answers from, which returns the clone of a named repository for an account, or nil when no source holds one that exists. Forge routing asks it for a repository whose worktree Forge does not know or no longer knows, which is what a repository that moved looks like ([[#h:shared-commands][Shared commands]]). Candidates are deduplicated by true path, so listing the same directory twice under different names, or through a symbolic link, yields one entry. A label shared by two candidates is replaced with the abbreviated directory, which is what then appears in completion, so no two projects offer the same string.

The function ~agent-project-read~ asks for one of those candidates. It takes the account, the text of the thing being routed, the completion prompt, a callback and an optional suggested directory, and calls the callback with the directory of the project chosen. A suggestion is offered first, which makes it what a bare =RET= answers, and it joins the candidates when no source holds it, so a caller that worked its directory out for itself leads the choice instead of bypassing it. Nothing is ranked when a suggestion is given, since a caller that already knows the project has no use for a model's opinion of it. It answers through the callback even when nothing is ranked, so every caller reads the answer the same way: the directory arrives in the callback, never as a return value. An account whose sources contribute no candidate at all raises an error rather than offering an empty prompt.

The candidates are ordered by a model before completion only when there is something to order them by: the routed text must hold more than whitespace, and at least one candidate must carry a description holding more than whitespace. A blank string counts as no text on either side, so candidates that came from path patterns alone, or from registry entries whose summary, aliases, keywords and Slack channels are all empty, go straight to completion and cost no request. An empty summary alone is not enough: the keywords and channels are appended to it, so an entry recording a blank summary and one keyword still carries text and is still ranked. When the request is made, ~agent-project-ranking-model~ and ~agent-project-ranking-backend~ name the model and the =gptel= backend it runs on; they default to ~gemini-flash-lite-latest~ on the ="Gemini"= backend, and ranking requires =gptel=, which is otherwise an optional dependency. The model is asked for the candidate labels, comma separated, most likely first. A name it returns is matched to the label it equals, and failing that to the shortest label it starts, so a name the model shortened still finds its project while a label that is itself the start of another still names its own. The candidates it names move to the front of the completion list in the order it gave them, each appearing once however often it is named, and the rest keep their original order behind them, so an answer that names only some projects, repeats one, or invents a label never hides a project. A request that fails is reported in the echo area and leaves the original order standing, so a ranking failure costs order rather than the whole action.

The =gptel= classifier requests used by backtrace debugging and project ranking ignore reasoning-block callback events and parse only the final response text. The optional =agent-chief= module runs a periodic, auditable chief-of-staff workflow. Emacs owns the schedule, explicit state, and notifications. In the default =session= mode, the selected backend is an ordinary long-lived Claude Code or Codex session that receives heartbeat prompts and remains available for normal conversation.

~agent-chief-backend~ selects =codex= or =claude-code=. ~agent-chief-mode~ defaults to =session=; set it to =stateless= to use the older one-shot JSON-decision path. ~agent-chief-interval~ controls the timer interval in seconds. ~agent-chief-directory~ is the working directory for chief sessions and one-shot calls; by default it uses =/Users/pablostafforini/My Drive/Epoch/= when that directory exists, falling back to ~user-emacs-directory~ otherwise. ~agent-chief-session-instance-name~ defaults to =chief= and is used as the instance name for the dedicated interactive session.

~agent-chief-state-file~ is an Org file used as the durable, inspectable state store; =agent-chief= never writes opaque memory. Day plans and manual notes are appended there and, when a chief session is live, submitted into that session as conversational context.

State context treats only a =Plan YYYY-MM-DD= heading dated today as current. Older plan headings are supplied as historical context, not active obligations, unless restated in today's plan.

~agent-chief-record-model-state-updates~ controls whether model-proposed state updates from stateless ticks are appended to the state file. It defaults to nil because periodic model observations are not user-approved durable memory. Use explicit notes and day plans for ordinary state updates.

~agent-chief-context-functions~ is the extension point for agenda, task, calendar, project, or custom status snippets. Each function is called with no arguments and should return a string. Nil and empty strings are ignored. The state file is included separately, truncated to ~agent-chief-state-max-chars~ characters. ~agent-chief-max-turns~ limits Claude Code ticks; Codex ticks use the existing =codex exec= settings from =agent-codex=.

In session mode, ~agent-chief-start-session~ sends only a short conversational kickoff asking the model to ask for today's plan; it does not dump the state file or stateless JSON contract into the visible transcript. Heartbeat prompts ask the model to respond exactly =No nudge.= when no contact is warranted, or =Nudge: MESSAGE= when it should alert the user. The backend's ordinary notification event tells =agent-chief= when the response is complete; =agent-chief= then inspects the session text since the heartbeat and calls ~agent-chief-notify-function~ only for a nudge. The default notification function logs the message and uses =alert.el= when available. ~agent-chief-system-prompt~ is the standing instruction that makes the loop selective and forbids inventing obligations not present in the supplied context.

In stateless mode, backend output may include echoed CLI transcript text before the answer. The chief loop scans that output and uses the last valid JSON object with a =notify= field as the decision, so echoed response-schema examples do not confuse the parser.

The command ~agent-history~, labeled “open log” and bound to =l= in the Sessions column, opens the Agent Log menu for browsing, opening, searching, and resuming historical sessions across backends. Agent Log is an optional package: loading =agent= never requires it, ~agent-history~ loads it on demand, and invoking the command without Agent Log installed signals a clear error. The command ~agent-select-session~ opens the session switcher, which contains only existing session entries. The switcher lists every session in one flat list ordered by home-row key, whatever account each session runs under. A session is therefore found at the key it always answers to, rather than at a position that moves when a neighbor's account changes. #+vindex: agent-session-annotation-functions
Sessions can also carry a one-line annotation after their name, shown dimmed in the ~agent-session-annotation~ face. The text comes from ~agent-session-annotation-functions~, an abnormal hook: each function is called with a session buffer and returns a string, or ~nil~ to leave the session to the functions after it. The first non-nil answer is the one shown, and the functions after it are not called. =agent= renders whatever it returns and knows nothing about where the text comes from. Whitespace in the answer is collapsed to single spaces, so a multi-line answer cannot break the menu's layout, and an answer that is blank or not a string counts as no annotation. #+vindex: agent-session-state-summary-functions

The switcher keeps the session summary and adds two columns after it: the
age of the current state and a short state description published by the agent.
Ages use seconds, minutes, hours, or days (=12s=, =2m=, =1h=, =3d=), measured
from the last observed state transition. Repeated events reporting the same
state do not reset the age; neither do changes to either summary. An
unobserved transition has no age. Ages refresh every five seconds while the
menu is open.

The state description is explicitly authored by the working agent, for
example “Testing pagination fix” or “Waiting for your decision about bindings”.
It is not extracted from the chat and requires no separate summarizer.
Until an agent publishes an update, the column is blank. A prompt submitted
from Emacs or a changed native session identity clears the previous
description. A turn that starts without one, such as a reply to a
background-task notification, keeps it, as does a completed turn. Publication does not alter the state color or
its age, and a claim of completion remains the agent's report.

~agent-slack-context~, answers with the message text and no directory, since a
message names no project of its own: the project is read from the account's
sources and ranked by that text ([[#h:project-options][Project sources]]).

The command ~agent-act-on-forge-notification~ is the Forge counterpart of
~agent-act-on-slack-message~. Called on a notification in
~forge-list-notifications~, it starts a session in the working tree of the
repository that notification belongs to and inserts the issue or pull request
URL into the prompt without submitting it. It also accepts the topic at point,
so it works from a topic buffer or a Magit status buffer, and with a prefix
argument it sends the URL to a running session instead of starting one. Not
every notification is about a topic: Github also notifies about check suites,
commits and releases, and Forge records no topic for those. Such a notification
is routed as itself, because it names a repository to work in and a URL to
read; its title goes into the prompt with the URL, since the URL of a failed
workflow run names the page listing every run of the repository and the title
is what says which one this is. The
command is a thin wrapper over the routing layer described below: its
extractor, ~agent-forge-context~, reads the subject at point and answers with a
context suggesting the working tree, so the project reader opens on that clone
already selected: a bare =RET= starts there, and the same prompt is where a
different project is chosen instead. Routing a topic therefore ends in the same
choice as routing a Slack message or a backtrace, rather than starting a session
outright.

A Slack message has to be classified to find its project, whereas a Forge
notification already records its repository. Where that repository is cloned is
a second question, and it is asked in three steps. Forge answers first, from the
worktree it recorded; it records one only for a repository it has seen from a
local clone, and it forgets one whose path stopped being a worktree, which is
what moving a repository does to every path at once. The account's project
sources answer next, with ~agent-project-repository-directory~: they are where
the clones live, so they know the current path of a repository that moved and
the path of one Forge never saw. When neither knows, the context carries no
directory and the core reads a project from its text, which leads with the
repository's slug so that ranking puts the right project first. Nothing is
refused for want of a clone.

The command ~agent-act-on-email~, called on a message in a mu4e headers or
view buffer, starts a session in the project that message is about and inserts
the message's maildir path into the prompt without submitting it. With a
prefix argument it sends the path to a running session instead. The payload is
the path rather than the text of the mail because an agent can open that file
itself and read the headers, the body and any attachments from it, which no
excerpt pasted into a prompt would carry. Like Slack routing and unlike Forge
routing, the context names no directory: a message belongs to no project of its
own, so its extractor, ~agent-mu4e-context~, answers with the subject and the
sender as the text the project is ranked against ([[#h:project-options][Project sources]]).

The sender comes from the message's =:from= field, which =mu= returns as a
list of =(:email EMAIL :name NAME)= plists — one per sender, with the name
absent when the sender gave none — and reads as =Name <address>=, or as the
bare address when there is no name. Like its Slack and Forge counterparts, the
command loads its foreign package itself and says so when it is missing, since
the command is autoloaded and can therefore be called from a buffer that has
never loaded mu4e.

It signals an error when the message records no path — mu4e reports a missing
string field as the empty string rather than as nil, so an empty path counts as
no path — and when the recorded file cannot be read. A maildir file name
encodes the message's flags, so reading a message, or another mail program
touching it, renames the file, and mu's index can name a path that no longer
exists until it is reindexed. As with a stale Forge clone path, that is an
ordinary failure, and catching it here is better than handing the agent a path
it cannot open.

#+findex: agent-act-on-thing-at-point
#+vindex: agent-at-point-things
The menu binds no routing command directly. ~agent-act-on-thing-at-point~, bound to =t .= in the Tools column, walks ~agent-at-point-things~ and runs the extractor of the first entry whose predicate matches the current buffer: a backtrace in a =*Backtrace*= buffer, a Slack message in a Slack room buffer, a Forge notification or topic, an email in a mu4e headers or view buffer, or an org TODO heading. Every predicate answers from the buffer alone — the buffer name, the buffer-local variable =slack= sets on room buffers, the major mode, the org TODO state — so dispatch never loads a module to ask whether it applies, and the Forge and mu4e lookups run only in a buffer whose major mode can hold what they look for. A Magit buffer is one of those, and it can be current with =forge= not yet loaded; since forge's lookups are not autoloaded, the Forge predicate also checks that they are defined, and falls through to the next thing rather than failing when they are not. The predicate claims any notification, not only one about a topic, because the extractor routes the notification itself when Forge records no topic for it. The mu4e modes need no such check, because the files that define those modes require the one that defines the lookup. When nothing matches, the command signals an error naming those five kinds, in the order the table holds them.

Recognizing the thing, choosing the session, and delivering the payload are three separate layers. An extractor takes a continuation rather than returning a value, because extraction can require a network round-trip, and calls it with a context plist: =:directory= when the thing carries a working directory, as an absolute path, =:suggested-directory= when it worked one out and the user should still be asked, =:text= when it carries only text to choose a project from, =:payload= for what to send, =:submit= for whether to submit it, and an optional =:after= thunk run once the payload is delivered. Before extraction begins, the core resolves the backend and captures that backend's selected account as one pair. A later account switch cannot change which project sources this invocation reads, which matters for asynchronous extractors such as Slack. A context that names a directory starts its session there; one that suggests a directory, or names none at all, has its project read from the captured account's sources with ~agent-project-read~, led by the suggestion or ranked by the text. With a prefix argument the payload goes to a running session chosen by completion instead of a new one, so the same key routes a thing either way.

A running session already has a directory, so on that path the core tells the extractor not to resolve one, and an extractor that has to work for its directory leaves it out. That saves what the work costs: routing a backtrace to a running session asks no model which packages it implicates and prompts for none, and routing a Forge topic there no longer refuses a repository that was never cloned locally. The extractors that carry only text are unaffected, since the project they would otherwise pick is chosen after the session is, and only for a new one.

What each kind sends differs, because the payloads differ. A Slack permalink, a Forge topic URL and an email's maildir path are references to something the agent should read, so they arrive unsubmitted and you type the request next to them. A backtrace and an org TODO already are the request, so they submit.

A payload marked =:submit= reaches a *new* session as its initial prompt, handed to the backend at launch rather than typed into the terminal afterwards. Claude passes it on the CLI's command line, and Codex does too except when it is resuming a session or running through its app server, where it sends the prompt itself once the session is up. Either way the payload never races the terminal: nothing sequences typed input against a session whose process has only just been spawned, and these sessions often start in a directory the CLI has never opened, where it greets the user with a trust prompt that the typed text would answer instead of the model. A payload the context does not submit is typed in on both paths, since it is meant to sit in the prompt for the user to edit. A submitted payload reaching an already-running session is typed in and then submitted, because that session is past its startup and needs no hand-off at launch.

Because extraction can be asynchronous, the continuation may run long after the command was invoked, in whatever buffer the user has moved to since. The dispatcher therefore captures the invocation buffer and resolves the backend up front, before the extractor runs: the session adopts the backend of the buffer the thing was read from rather than of wherever the callback lands, no backend prompt appears in the middle of an asynchronous wait, and the =:after= thunk runs back in the invocation buffer, which starting a session has displaced as the current one. A thunk whose buffer has been killed meanwhile is dropped, since the thing it would act on is gone.

The commands ~agent-handoff~, ~agent-audit-project~, ~agent-debug-backtrace~, ~agent-act-on-slack-message~, ~agent-exit~, and ~agent-restart~ resolve a backend from the current session buffer or by prompting. This lets the same keybinding operate on Claude or Codex sessions without separate wrapper commands. The old per-backend command names (~agent-claude-handoff~, ~agent-codex-restart~, and so on) remain available as obsolete aliases. ~agent-exit~, bound to =x=, kills the session buffer after any configured before-exit skills finish. ~agent-exit-without-skills~, bound to =X=, uses the same exit path but inhibits the configured before-exit skills. It still checks for pending captured prompts and runs other before-exit functions. Neither command deletes the Emacs window that displayed the session.

~agent-handoff~ reads the backend's entry in ~agent-handoff-files~, kills the current session buffer, and starts a new session with the handoff prompt. By default the new session keeps the source directory. A handoff file can select another directory with YAML front matter:

#+begin_example
---
target-directory: ../other-project
---

Continue from this handoff.
#+end_example

The target can be absolute or relative to the source session directory, and it must name an existing directory. ~agent-handoff~ resolves and validates it before it kills the source session. Lisp callers can pass the optional ~TARGET-DIRECTORY~ argument instead; an explicit argument takes precedence over file metadata, and file metadata takes precedence over the source directory.

~agent-handoff-from-emacsclient~ accepts the source buffer name as its first =emacsclient= argument and the optional target directory as its second argument. This lets agent-authored handoff commands close the requesting session even though Emacs evaluates the form outside that buffer. If the source buffer name is unavailable, handoff closes the single existing session buffer for the source directory before starting the replacement session, which avoids the CLI's instance-name prompt in unattended loops.

~agent-restart~ kills the current session buffer and resumes the same session in place, preserving the session's directory, instance name, and any launch state the backend's ~:restart-options~ function captures. It reroutes sessions within the selected account pool without prompting. Otherwise it prompts when the active account differs from the session account, and it leaves the account unset when neither the session nor the global selection names one, so a session that ran under the backend's ambient default home is restarted there rather than pushed onto an account it never used.  Every precondition is checked before the old session is killed: restart refuses when a named account is no longer configured, when the account is logged out, or when no resumable session identity exists, and in each case the running session survives untouched. ~agent-audit-project~ prompts for a project directory and runs each skill in ~agent-audit-skills~ sequentially through the backend's non-interactive prompt runner. ~agent-debug-backtrace~ saves the current Emacs backtrace, asks =gptel= to identify likely packages, and submits instructions to fix the bug to a session started in the selected package source directory, or to a running session under a prefix argument. Its extractor, ~agent--backtrace-context~, schedules the identification to run after the current command rather than doing it inline, because saving the backtrace kills the =*Backtrace*= buffer, which exits the debugger's recursive edit and unwinds the calling frame. ~agent-setup-kill-on-exit~ arranges for a session buffer to be killed when its process exits, consulting the backend's ~:before-kill-check~ slot first. It is not a menu entry: each backend installs it, along with ~agent-disable-scrollback-truncation~ and, for Codex, ~agent-fix-rendering~, from its session-start hook, so the menu carries no buffer-maintenance commands.

~agent-restore-sessions~, bound to =O=, resumes the sessions that were live when the last Emacs died, whether it quit, crashed, or went down with the machine. Each Emacs records its live sessions in ~agent-session-registry-file~ whenever a session starts, learns its native id, or ends, so the record survives deaths that skip Emacs's exit hooks; batch Emacs records nothing. An Emacs counts as dead when no process has its pid and start time, because a reboot reuses pids. The first save after a restart turns the sessions of every dead Emacs into the restorable set, replacing the previous one unless the dead Emacs had no sessions. The command asks once before resuming each session with its backend, account, directory, instance, session id, and the launch state its backend's ~:restart-options~ captured. It skips sessions already live and keeps failed ones recorded so it can be run again. A session is recorded only once its native id is known, so one killed before its first status update cannot be restored.

~agent-before-exit-functions~ can delay ~agent-exit~ for cleanup work.
Each function receives the resolved backend and session buffer; returning nil
aborts the exit.
When a turn is active, Agent waits for it to finish before it submits the first
before-exit skill, so the skill cannot steer or abort the user's turn.  A
backend that reports both a stop and a later idle-prompt notification for one
turn advances the chain only once.
Once a forced session close proceeds, Agent kills the target buffer without
running buffer-local kill-query prompts, so stale session buffers do not survive
restart or exit workflows.

Set ~agent-before-exit-skill-name~ (a single skill) or
~agent-before-exit-skill-names~ (an ordered list) to submit interactive skills
before exiting matching sessions. Each entry in ~agent-before-exit-skill-names~
is either a skill-name string or a list whose car is the skill name and whose
cdr is a plist accepting ~:directories~ (restrict where that skill runs,
overriding ~agent-before-exit-skill-directories~) and ~:args~ (a string
appended to the submitted command). Set ~:receipt~ non-nil when the skill must
confirm its closeout result before the chain can continue. For example:

#+begin_src emacs-lisp
(setq agent-before-exit-skill-names
      '("session-learning-capture"
        ("update-log" :directories ("~/My Drive/Epoch")
                      :args "--auto" :receipt t)))
#+end_src

~agent-run-skill-before-exit~ uses each backend's registered skill command
prefix so Claude sessions receive slash commands and Codex sessions receive
dollar-prefixed skill commands, then submits the first applicable skill. The
skills run in order, each submitted after the previous one finishes, and the
session exits after the last. These submissions do not display the session, so
an exit chain continues in the background after the user switches away;
ordinary ready notifications are left unchanged while the chain runs. When
~agent-before-exit-skill-names~ is nil, ~agent-before-exit-skill-name~ is used
as a single-skill fallback. Leave ~agent-before-exit-skill-directories~ nil to
run an unscoped skill before exiting every session.

For a ~:receipt~ entry, Agent creates a private temporary directory and appends
~--receipt-file PATH~ to the submitted command. The skill must write one JSON
object to that path. Its ~status~ must be exactly ~success~, ~no-op~, or
~failure~; a failure receipt can include a ~message~. Agent advances the chain
or exits only after ~success~ or ~no-op~. A missing file, invalid JSON, unknown
status, or ~failure~ stops the chain, keeps the session open, and shows a
warning; a missing file is ignored while the backend's idle probe still shows
the session working, since that completion event belongs to an earlier turn. Agent removes the temporary receipt directory after reading it or
tearing down the session. Receipt gating is per entry: plain entries keep the
stop-event behavior. This lets a learning-capture entry run independently
before a receipt-gated bookkeeping entry. Repeating ~agent-exit~ while a chain
is active does not bypass it; it reports the chain's state in the echo area,
and ~agent-exit-without-skills~ is the explicit close that skips configured
skills. When ~agent-exit~ is called on a session that is still responding, the
chain arms in a waiting state and starts its first skill on the next stop
event; a message says so at arming time, since nothing else is visible until
the turn ends.

~agent-exit~ runs every applicable configured skill regardless of session
duration. ~agent-exit-without-skills~ is the only exit command that bypasses
the skill hook; it still runs other before-exit functions.

The chain is driven by session stop events and guarded by a watchdog. Each
submitted skill gets up to ~agent-before-exit-timeout~ seconds (default 600) to
finish; the watchdog restarts when the next skill begins. If the current skill
exceeds that interval, the watchdog warns but keeps the exit request armed. The
chain checks the result when the skill eventually finishes instead of losing
the requested exit because the skill ran for more than ten minutes. A gated
entry still needs an accepted receipt at that point.

Backends can veto that automatic close while the submitted skill invocation is
still visible as unaccepted prompt input. Codex uses this to avoid closing a
session when the dollar-prefixed skill name was inserted but not submitted,
while ignoring submitted command scrollback, visible placeholder text, and
autosuggestion text. The readiness check recognises the standard Codex prompt
markers (=›= and =❯=); a chain that stalls after the first skill usually means
the running Codex renders an unrecognised prompt marker.

A chain stays armed across stop events until its queue drains, so a chain
whose command was typed but never accepted would otherwise fire its next skill
into whatever the user does in that buffer later. A prompt the user sends from
the terminal therefore cancels any armed chain in that buffer, with a message.
Claude reports such prompts as a ~user-submit~ session event from its Return
key paths; Codex's submission hook runs for programmatic sends too, so it
reports plain ~submit~ events and cannot cancel a chain this way.

Backends can provide an atomic submit operation for before-exit commands.
Claude and Codex both target the resolved session buffer directly, insert the
skill command, and submit it before the terminal buffer is displayed again.
Codex delegates this to =codex.el='s target-buffer submit helper. Claude
inserts the command, waits ~agent-claude-submit-delay~ seconds with
~sleep-for~ (pending keyboard input cannot shorten it, as it would a
~sit-for~, and a Return that arrives too soon is folded into the inserted text
as a newline), and sends Return. It then checks the prompt line and re-sends
Return up to ~agent-claude-submit-retries~ times while the command is still
sitting there unsubmitted, since Claude Code occasionally swallows the first
one; the prompt marker's trailing space is a no-break space under =eat=.

The global minor mode ~agent-remote-mode~, in =agent-remote.el=, serves a touch-friendly control page so a phone can watch and unblock sessions. The page lists every live session with its state, backend, account and time in that state, waiting sessions first. Tapping a session shows the last ~agent-remote-output-lines~ lines of its buffer, refreshed every 1.5 seconds. A text box submits a reply through ~agent-submit~, and a row of keys sends single keystrokes to the session's terminal: escape, digits, arrows, return, tab, shift-tab, =y=, =n= and =C-c=. An escape sent to a Claude session goes through ~claude-code-send-escape~, so an interrupted turn is detected as it would be from Emacs. Because the page drives the session buffers themselves, it reaches Claude and Codex sessions under every account. Keys need a terminal session; a session without an EAT terminal accepts only text.

The session view's Restart button restarts the session under another account, for a session that has hit its usage limit while you are away. It lists the backend's pools and accounts with each account's latest weekly and session usage, marking accounts at their limit and disabling logged-out ones. Choosing one calls ~agent-restart-with-account~, which does what selecting the account with ~agent-account-select~ and then choosing it at the ~agent-restart~ prompt does: the choice becomes the selection for new sessions, a pool is routed to one of its members, and the session resumes its conversation under the new account. It never prompts in Emacs; it refuses a session with captured prompts, which the account change would orphan.

The server listens on ~agent-remote-listen-address~ and ~agent-remote-port~ (default 8787). The listen address defaults to every IPv4 interface, because the macOS Tailscale app does not deliver connections to a socket bound to the Tailscale address alone. Instead, the server closes without a response every connection whose peer is outside ~agent-remote-allowed-networks~, which defaults to =100.64.0.0/10=, the range Tailscale assigns to tailnet devices; devices on the local network cannot use it. ~agent-remote-host~ is the address the phone uses. When nil, it is this machine's Tailscale IPv4 address, obtained from ~agent-remote-tailscale-program~; if Tailscale is missing or disconnected, enabling the mode signals an error. Two checks keep web pages in a browser on the same machine from using the server: every request must name ~agent-remote-host~ and the port in its =Host= header, which defeats DNS rebinding, and every request that sends input must carry an =X-Agent-Remote= header, which a cross-origin page cannot add without a preflight the server never approves. There is no further authentication, so do not add networks that untrusted devices can connect from.

The page is =etc/agent-remote.html=, served from the source checkout. The =android/= directory holds a single-purpose Android app, "Agents", for phones without a browser. It shows only this page and cancels any navigation to another origin. =android/build.sh install= builds it with the Android command-line tools, without Gradle, and installs it over =adb=; =AGENT_REMOTE_URL= sets the page address it is built for.

** Orchestration run view

The command ~agent-run-open~, bound to =t o= in the Tools column of
~agent-menu~, opens an =orchestrate-review= run JSON file in a read-only
~agent-run-mode~ buffer. Select the private run file created by the skill;
the command remembers opened filenames for the current Emacs session and
does not scan temporary directories. Each run has its own view.

The view shows the recorded stage, phase, status, author and reviewer, and
the latest stage-level progress with the progress file's age. Pending delivery
reconciliation and a recorded incomplete return appear as attention items.
Old progress does not establish that an actor stopped. A returned implementation
is distinct from a completed run; the helper still owns verification evidence
and completion. This view does not validate the full workflow contract.

An unavailable or replaced session is labeled unavailable. Legacy version-2
runs remain readable, but actors without recorded identities cannot be linked.
File links open the run record, progress file, run directory, or repository.
The run format does not record ordinary spec/plan paths or blocker descriptions;
the view says so rather than looking through conversations to infer them.

Visible views refresh every five seconds; =g= refreshes immediately and =q=
quits the window. Killing a view cancels its refresh timer. A read failure
replaces the display with an explicit error, so stale data cannot appear current.
Only local files are supported. Run reads are limited to 4 MiB, and progress
reads to the final 16 KiB. The view never submits prompts, advances phases,
reads transcripts, inspects internal tasks, or starts workers.

** Branch navigation
:PROPERTIES:
:CUSTOM_ID: h:branch-navigation
:END:

#+findex: agent-resume
#+findex: agent-create-branch
#+findex: agent-switch-branch
A branch is a session forked from another one: it starts with the parent's whole conversation and then diverges. Branching lets you try a different approach without losing the state you built up, and the three commands here work the same way whichever backend the session belongs to.

~agent-create-branch~, bound to =b n=, forks the session in the current buffer and opens the fork in its own buffer under an instance name derived from the time of the fork. By default the branch shares the parent's working tree, which is what starting a second session in the same project would give you. With a prefix argument it also creates a git worktree on a fresh branch under ~agent-branch-worktree-directory~ and runs the fork there, so that destructive git operations in one branch cannot disturb the other. The worktree starts at the parent's HEAD, so uncommitted parent changes are not carried into it; use the isolated form when concurrent git work across branches is a real concern, and the default otherwise. Before the fork starts, the backend's ~:prepare-fork~ slot makes the parent session visible from the new directory, which is what a backend that stores its transcripts per project directory needs in order to resume a session recorded elsewhere.

~agent-switch-branch~, bound to =b s=, shows every session sharing a fork ancestor with the current one as an indented tree, each entry carrying its first prompt and its timestamp and the session you are in marked with an asterisk, and switches to the selected session: to its live buffer when it still has one, and otherwise by resuming it in a new buffer. It reports that there is nothing to navigate when the current session has no relatives.

~agent-resume~, bound to =R=, resumes a past session of the current backend, or of a backend it asks for when no session buffer names one, and passes its prefix argument through to the backend, where it means the most recent session.

Both backends supply the lineage these commands read, through the ~:session-headers~ slot, and each derives it from what its CLI already records. Claude Code writes one transcript per session inside a per-project directory, so the scan reads the first line of each transcript in the project the current session belongs to. Codex writes one rollout file per session, all under a single sessions directory, so the scan reads the ~session_meta~ record opening each rollout, keeps the ones whose recorded working directory matches, and takes the parent from ~forked_from_id~. Because that directory holds every Codex session on the machine, the scan is bounded by a start timestamp when the caller only needs one session's descendants.

Codex records subagent threads with the same ~forked_from_id~ field, and those are deliberately left out of the tree. They are forks as far as the file format is concerned, but they are not branches of your conversation: they are threads the model spawned to do work on its own, and offering to switch into one would be offering something a user never chose to create.

** Org TODO commands
:PROPERTIES:
:CUSTOM_ID: h:todo-commands
:END:

#+findex: agent-batch-todos
#+findex: agent-send-todo-at-point
The =agent-todo= module turns Org TODO entries into work for an AI session, and both of its commands work with either backend.

~agent-send-todo-at-point~ formats the heading and body of the TODO at point as a prompt and submits it to a session started for it; it is not a menu entry of its own, since the menu reaches the same routing through ~agent-act-on-thing-at-point~. With a prefix argument it submits the prompt to a running session chosen by completion. Like a Slack message, a TODO names no directory, so the project is read from the account's sources and ranked by the TODO's own text ([[#h:project-options][Project sources]]). It no longer looks for the session belonging to the current file's project: an Org file of tasks rarely sits in the repository those tasks are about. When ~agent-todo-in-progress-keyword~ is set, the heading moves to that keyword once the prompt has been delivered. The heading is remembered as a marker, so the move lands on the heading the prompt came from however far point has travelled while the project was being chosen. A heading deleted in the meantime is left alone: the state change happens after the session exists but before it is shown, so an error there would leave a running session unshown.

~agent-batch-todos~, bound to =p b=, collects several TODO entries and runs them one after another without an interactive session. It infers its scope by itself — the region when one is active, the subtree when the buffer is narrowed, and the whole buffer otherwise — then asks for a working directory, and confirms the number of entries before starting unless you selected them as a region, where the selection is confirmation enough. Each entry runs through the resolved backend's ~:exec-prompt~ slot, its raw output is written to a numbered file under a timestamped directory in ~agent-todo-log-directory~, and a summary buffer collects every entry's status, duration, cost, and output when the queue is empty.

Cost appears per entry only for backends whose CLI reports it. Claude's non-interactive runs report a dollar figure and it is shown; =codex exec= reports none, so Codex entries render an em dash in place of a cost and contribute nothing to the total.

The command ~agent-chief-start-session~ starts or reuses a dedicated Claude Code or Codex session using ~agent-chief-session-instance-name~, sends the chief-of-staff operating contract into the session, asks the model to request today's plan there, and starts the heartbeat timer. The command ~agent-chief-switch-to-session~ jumps back to that session so the user can reply normally.

The command ~agent-chief-start~ starts only the repeating Emacs timer. Without a prefix argument it also schedules an immediate tick; with a prefix argument, it waits ~agent-chief-interval~ seconds before the first tick. ~agent-chief-stop~ cancels the timer. ~agent-chief-tick~ runs one check using ~agent-chief-mode~. ~agent-chief-session-heartbeat~ forces a session-mode heartbeat, while ~agent-chief-stateless-tick~ forces one stateless JSON-decision check.

The command ~agent-chief-open-state~ opens the auditable Org state file. ~agent-chief-add-note~ appends a manual note, and ~agent-chief-set-day-plan~ appends today's plan. When a chief session is active, both commands also submit the new context into that session. These commands are intentionally simple: the durable source of truth remains ordinary text that can be reviewed, edited, and audited outside the model.

The function ~agent-register-backend~ registers an AI tool by constructing an ~agent-backend~ struct from keyword arguments. Backend modules call it at load time. Keywords are validated against the struct's slot names, and the required slots ~:buffer-p~, ~:find-all-buffers~, and ~:start-session~ are checked so the shared session layer can rely on a consistent interface.

The full slot set is: identity and presentation (~name~, ~label~, ~icon~, ~program~), buffer discovery (~buffer-p~, ~find-all-buffers~, ~find-buffers-for-dir~), session lifecycle (~start-session~, ~session-identity~, ~restart-options~), send primitives (~send-string~, ~send-return~, ~submit~), session state probes (~waiting-p~, ~busy-p~, ~background-tasks-p~, ~display-name-suffix~, ~notify~), accounts (~account-env-var~, ~accounts~, ~account-file~, ~shared-config-items~, ~canonical-home~, ~account-init~, ~credential-file~, ~login-args~, ~usage-fetch~), skills (~run-prompt~, ~exec-prompt~, ~skill-roots~, ~skill-command-prefix~), session history (~session-headers~, ~session-prompt~, ~resume~, ~prepare-fork~), integration hooks (~sync-theme~), and exit safety (~before-exit-ready-to-close-p~, ~before-kill-check~, ~idle-p~).

The ~:start-session~ slot starts a new session parameterized by an ~agent-session~ identity struct, optionally with an initial prompt or a resume id. The ~:session-identity~ slot returns a live session buffer's CLI session id, used by ~agent-restart~ to resume in place. ~agent-start-session~ is the core dispatcher that starts a session through its backend's ~:start-session~ function, passing any extra backend-specific options through. The ~:send-string~ slot inserts text into a session's prompt without submitting it, ~:send-return~ submits the pending prompt, and ~:submit~ atomically inserts and submits; the core wrappers ~agent-send-string~, ~agent-send-return~, and ~agent-submit~ dispatch through these slots and emit the corresponding session events.

The slots that carry the unified session commands are all optional, and a backend that omits one simply does not support the commands dispatching on it. ~:resume~ resumes a past session, receiving the command's prefix argument, and backs ~agent-resume~. ~:session-headers~ returns a hash table mapping session id to a plist of ~:session-id~, ~:forked-from~ and ~:timestamp~, called with a session buffer and optionally with the one session whose descendants the caller cares about, so a backend that keeps every session in one directory can bound its scan; ~:session-prompt~ enriches one such header with the session's ~:first-prompt~. Together they back ~agent-switch-branch~ and the branch check before a kill. ~:prepare-fork~ makes a session recorded under one directory visible from another, which is what lets an isolated branch run in a fresh worktree. ~:exec-prompt~ runs a prompt non-interactively and calls back with a plist of ~:exit-code~, ~:duration~, ~:text~ and ~:raw~; ~agent-batch-todos~ runs through it.

~agent-display-name~ returns a human-readable label for a session buffer. It starts with the project name, adds an instance name when needed to disambiguate duplicates, and lets backends append their own suffixes. The Claude backend uses this to expose branch identity in the modeline and switcher.

~agent-parse-skill-frontmatter~ reads =SKILL.md= frontmatter shared by Claude and Codex skill runners. It recognizes names, descriptions, argument hints, argument sources, argument choices, defaults, multiplicity, user-invocable flags, and model overrides.

~agent-svg-icon~ renders SVG strings as inline images, using the current face foreground when the SVG uses =currentColor=. Backends use this for modeline and transient display and can fall back to text abbreviations when SVG rendering is unavailable.

The Claude and Codex status helpers are intended for modeline integrations such as =doom-modeline=. Claude status functions read the current session status JSON and expose model, reasoning effort, cost, context, duration, and token information. Claude usage functions expose account-level utilization returned by the Anthropic usage endpoint. Codex status functions expose the current session model, reasoning effort, and elapsed session duration; the model helper falls back to the configured model when the session has no live model value. When Codex has no explicit reasoning-effort override, the status helper reports Codex's default =medium= effort. The session switcher uses backend busy, input-readiness, and background-work detectors to avoid showing actively responding sessions as waiting, and to distinguish truly idle waiting sessions from sessions that are accepting input while background terminals, agents, or tasks are still running. For Claude that evidence comes from the session's transcripts, read incrementally on each status poll: a background shell, Monitor, workflow, or background agent counts from the tool result that starts it until a task notification, a TaskStop result, or the end of the subagent that started it closes it, including tasks started by subagents and teammates in their sidechain transcripts, and only tasks started since the CLI process began count. The Remote Control task UI also counts. The footer's task counts are not used, because its =← N agents= indicator counts agents across every session on the machine. Claude Code exposes no hook or statusline field for background tasks, so the transcript format, which is internal to Claude Code, is pinned by the tests. A session counts as waiting only when it is blocked on the user, meaning it has stopped and will not proceed until the user submits something. Being able to queue text mid-turn is not waiting, since both CLIs accept typed input at any point. Codex app-server sessions learn turn boundaries from the JSON-RPC stream, so an inactive turn on a live app server is authoritative for waiting and an active turn is authoritative for busy, regardless of whether the prompt accepts input. Terminal sessions have no such signal and fall back to the session-event state machine and to scanning rendered status text. For Claude, ~agent-claude--terminal-waiting-p~ reports idle when the rendered tail shows the input prompt and no running-turn spinner line (a glyph, a verb ending in an ellipsis, and a parenthesised elapsed time, e.g. =✢ Billowing… (4m 35s)=; the older =esc to interrupt= hint and the background-task =esc to give additional instructions= prompt also count as running). It is registered as the backend's ~:idle-p~ — not ~:before-exit-ready-to-close-p~, whose veto runs on every chain step, where the screen's redraw lag behind the Stop hook would strand the chain — and consulted only by the before-exit chain and the escape interrupt check described in [[#h:session-state-machine][Session state machine]]: when arming, a busy session whose terminal affirms idleness arms immediately, and the watchdog advances a chain stranded in ~waiting-for-idle~ whose stop event never arrived — a turn the CLI accepts and then drops, for instance at the context limit, fires no Stop hook. Screen scraping is not reliable enough to drive the switcher on its own, so display state stays with the session-event state machine; the interrupt check consults the screen only right after the user sends an escape. A ~busy~ state younger than ~agent-claude-terminal-idle-grace~ seconds is trusted over the screen, since the spinner takes a moment to appear after a submission. Codex prompt submission clears the previous waiting marker at the target buffer, so a session does not remain colored as waiting after the user sends a new prompt.

* Transient menu
:PROPERTIES:
:CUSTOM_ID: h:transient-menu
:END:

#+findex: agent-menu
~agent-menu~ is a single static prefix defined in =agent.el=, laid out in four columns: Sessions with Account beneath it, Current session, Tools with Prompts beneath it, and Options. Nothing in the layout depends on which backends are loaded, because every command in it is backend-agnostic. Each one resolves a backend from the current session buffer, or asks when nothing names one, and then dispatches through that backend's slots, so the same key operates on a Claude session and a Codex session alike. There is no longer any mechanism for a backend module to add entries to the menu, and this is deliberate: a backend contributes an implementation for a slot, and the command that calls that slot lives in =agent.el=.

In the Options group, =-c= selects an account. It acts on the current or prompted backend, while its value shows every registered backend's current account at once, so one entry replaces the per-backend account selectors the menu used to carry. The infix shares its implementation with the per-backend account commands in =agent-account.el=, and syncs the selected account's config home as soon as the selection is made.

Boolean menu infixes use a shared transient class that toggles the bound variable each time it is invoked. The theme-sync infix additionally calls ~agent-sync-theme-now~ when enabling theme sync, so backend configuration files are updated immediately.
