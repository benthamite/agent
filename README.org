This manual describes the features and customization options for the Emacs Lisp package =agent.el=.

* Overview
:PROPERTIES:
:CUSTOM_ID: h:overview
:END:

=agent.el= collects the Emacs integration layer for AI coding command-line tools. It provides a shared session model, a unified transient menu, notification handling, terminal helpers, backend modules for Claude Code and Codex, and an optional chief-of-staff loop.

The package is split into a small backend-agnostic core and focused modules:

| Module               | Role                                                                                                                                                                                                                        |
|----------------------+-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| =agent.el=           | Core: backend registry, session identity and state machine, session keys and teardown, unified orchestration commands (handoff, restart, exit, skills, audits, backtrace debugging), transient menu, alerts, theme sync    |
| =agent-account.el=   | Multi-account support shared by all backends: selection, persistence, per-account config homes, symlinked shared state                                                                                                      |
| =agent-capture.el=   | Persisted Org prompt capture, keyed to the session it targets                                                                                                                                                               |
| =agent-slack.el=     | Slack-message-to-project routing: classifies a Slack message with =gptel= and starts a session in the matching project                                                                                                      |
| =agent-snippet.el=   | Yasnippet TAB expansion and snippet insertion in eat-based session buffers                                                                                                                                                  |
| =agent-claude.el=    | Claude Code backend: integrates =claude-code.el= with status and usage polling, branch navigation, batch TODO processing, hook setup, and ~agent-claude-mode~                                                               |
| =agent-claude-cli.el= | Quarantined undocumented Claude CLI conventions: Keychain credential naming, the usage API endpoint, the =~/.claude/projects/= directory encoding, transcript JSONL parsing, and the =.claude.json= merge engine            |
| =agent-codex.el=     | Codex backend: integrates =codex.el= with theme sync, =codex exec= execution, =config.toml= helpers, modeline helpers, and ~agent-codex-mode~                                                                               |
| =agent-chief.el=     | Inspectable chief-of-staff loop: Emacs owns timers, state, context collection, and notifications, while Claude Code or Codex provides one-shot judgment on each tick                                                        |

The main workflow is to load =agent.el=, require the backend modules you use, and enable their minor modes (see [[#h:minor-modes][Backend minor modes]]); loading a backend module installs nothing by itself. Once the Claude and Codex modules are active, =M-x agent-menu= and =M-x agent-start-or-switch= operate across both tools. Sessions are grouped by account when the backend exposes account metadata, highlighted when waiting for input, and disambiguated by project and instance name when several sessions share a directory.

The package depends on =transient= for menus, =consult= for completion, =claude-code.el= for the Claude backend, and =codex.el= for the Codex backend. All four are declared in the package metadata so that the package manager builds =agent= with them available; the backend modules hard-require their respective backend at load time. Optional integrations use packages such as =yasnippet=, =doom-modeline=, =gptel=, =agent-log=, and =monet= when those are available.

* Architecture
:PROPERTIES:
:CUSTOM_ID: h:architecture
:END:

** Session identity
:PROPERTIES:
:CUSTOM_ID: h:session-identity
:END:

#+findex: agent-session
#+findex: agent-session-buffer-name
Every live session buffer carries a buffer-local ~agent-session~ struct, captured once when the session starts. Its slots are ~backend~ (the backend symbol), ~account~ (the account name, or nil for the default), ~directory~ (the abbreviated project directory), ~instance~ (the instance name, or nil), and ~id~ (the CLI session id, or nil until known). The function ~agent-session~ returns the struct for a buffer, and ~agent-session-buffer-name~ derives the canonical buffer name from the identity. All orchestration code reads identity from this struct; nothing parses buffer names.

** Session state machine
:PROPERTIES:
:CUSTOM_ID: h:session-state-machine
:END:

#+findex: agent-session-event
Each session buffer tracks its readiness in the buffer-local variable ~agent--session-state~, which is one of ~unknown~, ~busy~, ~awaiting-input~, or ~closing~. Buffers start as ~unknown~ and stay there until a session event arrives, so a state that was never observed is never presented as one that was; the session switcher renders such sessions with ~agent-unknown~ and ~agent-jump-to-waiting~ skips them. All transitions go through ~agent-session-event~, which accepts the events ~stop~, ~idle-prompt~, ~blocked~, ~submit~, ~activity~, and ~exit-request~. An ~activity~ event marks the session busy on evidence that it is working. It exists because Claude Code publishes no turn-start hook, so turns the user did not type — a turn resumed after a background task finishes, for instance — are otherwise unobservable; the ~notify-emacs-state.sh~ wrapper forwards ordinary lifecycle events (~PreToolUse~, ~MessageDisplay~, ~UserPromptSubmit~) in their place, debounced so that high-frequency events cost one call per window. A ~blocked~ event marks the session as waiting on the user without firing a ready alert, and is used for permission and elicitation dialogs: Claude reaches those from inside a turn with a tool call still in flight, so nothing else reports them as waiting even though they proceed only once the user answers. Backends translate raw CLI notifications into these events and never set session state directly. A ~stop~ or ~idle-prompt~ event first offers the transition to the before-exit chain; when the chain consumes it, ready alerts and display refreshes are suppressed. Ready alerts fire only for ~idle-prompt~ events, and a ~submit~ event delivered while the session is already busy is ignored, because backend submission hooks can fire more than once per submission.

** Session teardown and leak policy
:PROPERTIES:
:CUSTOM_ID: h:session-teardown
:END:

Session resource cleanup has a single owner: ~agent--session-teardown~ runs a session buffer's ~agent--teardown-functions~ exactly once, whether the buffer is killed first or the CLI process exits first, then releases the session's home-row key. Backends and features register their per-session resources (status poll timers, monet servers, before-exit chains) as teardown functions instead of installing their own kill-buffer hooks. Claude buffers also adopt any already-running Monet server when ~agent-claude-mode~ is enabled or reloaded, so teardown owns sessions that predate the current Agent code. The monet websocket server needs one extra guard: when the Claude client disconnects, ~monet--on-close-server~ drops the session from monet's own table before teardown can look it up, so an =:after= advice closes the listening server at that moment rather than letting it escape to the GC safety net. Resources that escape teardown are not silently reaped: safety nets report each one through a =Warnings= buffer entry tagged =agent=, naming the leaked resource. A leak warning therefore indicates a lifecycle bug worth reporting, not routine noise. The Monet GC sweep identifies servers by ownership, not by process name: Agent registers every server process it sees monet create or adopt, and the sweep only ever reaps registered servers that have lost their monet session. Websocket servers belonging to other packages (atomic-chrome, org-roam-ui) share the generic =websocket server on port N= process name but are invisible to the sweep and can never be reported or killed as monet leaks.

** Account model
:PROPERTIES:
:CUSTOM_ID: h:account-model
:END:

#+findex: agent-account-select
#+findex: agent-account-init
Multi-account state lives in =agent-account.el= and is keyed by backend. Each backend declares an accounts alist mapping account names to per-account configuration homes (~agent-claude-accounts~, ~agent-codex-accounts~), a persisted selection file that survives Emacs restarts (~agent-claude-account-file~, ~agent-codex-account-file~), and the environment variable that points the CLI at the selected home: =CLAUDE_CONFIG_DIR= for Claude Code and =CODEX_HOME= for Codex. Account homes keep credentials separate, while shared state (settings, hooks, skills, sessions, history) is symlinked from the backend's canonical home so it remains available after switching accounts; conflicting account-local files are backed up to timestamped =*.agent-backup-*= siblings first. ~agent-account-select~ persists a choice and syncs the account home, and ~agent-account-init~ prepares or repairs a home. When the merge engine reads a home's =.claude.json=, a parse failure is retried once after a short delay before warning, since a running CLI rewrites the file frequently and a read can land mid-write. The account a session was started under is recorded in its ~agent-session~ struct, so restart and handoff preserve it even after the global selection changes.

** Backend minor modes
:PROPERTIES:
:CUSTOM_ID: h:minor-modes
:END:

#+findex: agent-claude-mode
#+findex: agent-codex-mode
The global minor modes ~agent-claude-mode~ and ~agent-codex-mode~ own every hook, advice, timer, and notification handler their backend installs. Loading =agent-claude.el= or =agent-codex.el= installs nothing; the modes must be enabled explicitly. Disabling a mode removes its hooks and advice symmetrically and restores the backend's previous notification function, leaving running sessions untouched. A typical setup:

#+begin_src emacs-lisp
(use-package agent
  :config
  (require 'agent-claude)
  (require 'agent-codex)
  (require 'agent-chief)
  (agent-claude-mode 1)
  (agent-codex-mode 1))
#+end_src

#+vindex: agent-act-on-slack-message-backend
#+vindex: agent-epoch-project-registry-file
#+vindex: agent-epoch-projects-root
#+vindex: agent-prompt-capture-directory
#+vindex: agent-prompt-capture-auto-save-delay

The user option ~agent-protect-buffers~ is a boolean that defaults to ~t~. When enabled, killing a live AI session buffer prompts for confirmation through ~agent-protect-buffer~. Buffers whose processes have already exited are allowed to die without the prompt.

The user option ~agent-alert-on-ready~ is a boolean that defaults to ~nil~. When enabled, backend notification handlers can call ~agent-notify~ to emit visual and/or audible alerts when a session is waiting for input. Codex's own terminal-bell notification path is routed through the same alert setting. ~agent-alert-style~ selects ~visual~, ~sound~, or ~both~; it defaults to ~both~. ~agent-alert-sound~ defaults to ~nil~; set it to a sound file to enable sound alerts. ~agent-alert-sound-player~ optionally names an external sound player when Emacs sound support is unavailable.

The user option ~agent-backtrace-file~ controls where ~agent-save-backtrace~ and ~agent-debug-backtrace~ write Emacs backtraces. It defaults to a file in ~temporary-file-directory~.

The unified orchestration commands share one set of options across backends. ~agent-handoff-files~ maps backend symbols to the handoff files read by ~agent-handoff~. ~agent-audit-skills~ lists the audit skills run by ~agent-audit-project~, and ~agent-audit-project-directories~ stores completion candidates for the audit directory prompt. ~agent-debug-backtrace-model~ and ~agent-debug-backtrace-backend~ configure the =gptel= request used by ~agent-debug-backtrace~ to identify likely culprit packages from an Emacs backtrace. ~agent-act-on-slack-message-model~ and ~agent-act-on-slack-message-backend~ configure the =gptel= request used by ~agent-act-on-slack-message~ to select an Epoch project from the Slack message at point.

The user options ~agent-epoch-project-registry-file~ and ~agent-epoch-projects-root~ configure Slack-message project routing. Both default to nil; Slack routing is unavailable until they point at a JSON project registry and the root directory containing the canonical project files.

The user option ~agent-prompt-capture-directory~ controls where ~agent-capture-prompt~ stores per-session Org files. Each file is keyed by backend, account, project directory, and session instance, so prompts are linked to the session they target and remain available after Emacs restarts. ~agent-prompt-capture-auto-save-delay~ controls the idle delay before capture buffers are saved automatically.

The user option ~agent-sync-theme~ is a boolean that defaults to ~nil~. When enabled, theme changes in Emacs are persisted through each registered backend's theme-sync handler. This updates configuration files for new or restarted CLI sessions without sending theme commands into active terminal conversations.

The user option ~agent-sigwinch-delay~ is a number of seconds and defaults to =0.5=. It controls how long ~agent-fix-rendering~ waits before sending =SIGWINCH= to a terminal process. Increase it if an AI CLI reads the terminal size before the =eat= window has settled.

Snippet helpers use =yasnippet= and =consult-yasnippet= only when those optional packages are loaded.

#+vindex: agent-claude-batch-permission-mode

#+vindex: agent-claude-batch-system-prompt
#+vindex: agent-claude-batch-model
#+vindex: agent-claude-org-todo-in-progress-keyword
The Claude backend options control account selection, session metadata, non-interactive execution, and branch workflows. ~agent-claude-accounts~ is an alist of account names to Claude configuration directories, and ~agent-claude-account-file~ stores the selected account across Emacs sessions. Use ~agent-claude-select-account~ or the account infix in ~agent-menu~ to switch accounts before starting a new session. Both commands are thin wrappers around ~agent-account-select~, which persists the choice and syncs the account's config home; ~agent-account-init~ prepares or repairs any backend's account home.

Status and usage polling are controlled by integer intervals. ~agent-claude-status-interval~ defaults to =5= seconds and reads status JSON emitted by the bundled statusline script. ~agent-claude-usage-interval~ defaults to =300= seconds and backs off up to ~agent-claude-usage-max-interval~, which defaults to =900= seconds. Usage polling reads the account's OAuth token from the macOS Keychain, so accounts authenticated with an API key rather than an OAuth subscription—whose OAuth Keychain store is an empty JSON object—are silently skipped rather than treated as a broken lookup. The Keychain lookup runs from the temporary-file directory, so a poll that fires while the current buffer's =default-directory= names a deleted worktree cannot break the subprocess spawn.

Batch execution options are passed to =claude -p=. ~agent-claude-batch-permission-mode~ defaults to ="auto"=, ~agent-claude-batch-max-turns~ defaults to =30=, and the allowed tool, model, and appended-system-prompt options let you narrow or expand what non-interactive Claude tasks may do.

Branch and buffer safety options default conservatively. ~agent-claude-warn-kill-with-branches~ defaults to ~t~ and warns before killing a session that belongs to a branch tree. ~agent-claude-fork-worktree-directory~ defaults to a cache directory so isolated branch worktrees do not interfere with cloud sync.

Claude hook setup is explicit. ~agent-claude-settings-file~ names the settings file updated by ~agent-claude-setup-config~ and the individual ensure commands. ~agent-claude-hook-wrapper~ points to the upstream =claude-code= hook wrapper, while ~agent-claude-statusline-script~ points to the bundled statusline helper. ~agent-claude-status-directory~ controls where the helper writes per-buffer status JSON files. The statusline setup refreshes an existing agent-owned =claude-code-statusline.sh= command, which keeps the settings file correct after the package moves or is renamed, while preserving unrelated custom Claude statusline commands. Loading the backend does not modify Claude Code configuration.

** Codex backend
:PROPERTIES:
:CUSTOM_ID: h:codex-options
:END:

#+vindex: agent-codex-accounts
#+vindex: agent-codex-account-file
#+vindex: agent-codex-skill-directories
#+vindex: agent-codex-exec-approval-policy
#+vindex: agent-codex-exec-sandbox-mode
#+vindex: agent-codex-exec-skip-git-repo-check
The Codex backend options control account selection, skill discovery, and non-interactive execution. ~agent-codex-accounts~ is an alist of account names to Codex home directories, and ~agent-codex-account-file~ stores the selected account across Emacs sessions. Account homes keep credentials such as =auth.json= separate, while shared Codex state such as =config.toml=, =hooks.json=, skills, sessions, and =history.jsonl= is symlinked from =~/.codex/= so hooks, skills, project trust, and chat history remain available after switching accounts; the Claude backend shares state between account homes the same way. When an account-local file conflicts with a shared item, it is backed up to a timestamped =*.agent-backup-*= sibling before the symlink is created, so no local state is silently lost. Use ~agent-codex-select-account~ or the Codex account infix in ~agent-menu~ to switch accounts before starting a new session. Both commands are thin wrappers around ~agent-account-select~, which persists the choice and syncs the account's config home; ~agent-account-init~ prepares or repairs any backend's account home.

~agent-codex-skill-directories~ is a list of additional directories scanned for Codex skills. The backend also scans standard Codex skill locations and project-local skill directories.

~agent-codex-exec-approval-policy~, ~agent-codex-exec-sandbox-mode~, and ~agent-codex-exec-skip-git-repo-check~ configure the non-interactive Codex calls used by skill and audit workflows. The approval policy is passed as a top-level Codex CLI option before the =exec= subcommand, while the sandbox and repository-check options are passed to =codex exec= itself.

The =gptel= classifier requests used by backtrace debugging and Slack routing ignore reasoning-block callback events and parse only the final response text. Backtrace debugging sends the model a truncated excerpt of the backtrace rather than the full contents: each line is cut at 400 characters and the excerpt is capped at 100,000 characters, since backtraces can embed multi-megabyte printed objects that exceed API payload limits, while the frame names at the start of each line suffice to identify packages. The agent session itself still receives the path to the complete backtrace file.

** Chief-of-staff loop
:PROPERTIES:
:CUSTOM_ID: h:chief-options
:END:

#+vindex: agent-chief-backend
#+vindex: agent-chief-mode
#+vindex: agent-chief-interval
#+vindex: agent-chief-directory
#+vindex: agent-chief-session-instance-name
#+vindex: agent-chief-state-file
#+vindex: agent-chief-context-functions
#+vindex: agent-chief-state-max-chars
#+vindex: agent-chief-max-turns
#+vindex: agent-chief-notify-function
#+vindex: agent-chief-record-model-state-updates
#+vindex: agent-chief-system-prompt
The optional =agent-chief= module runs a periodic, auditable chief-of-staff workflow. Emacs owns the schedule, explicit state, and notifications. In the default =session= mode, the selected backend is an ordinary long-lived Claude Code or Codex session that receives heartbeat prompts and remains available for normal conversation.

~agent-chief-backend~ selects =codex= or =claude-code=. ~agent-chief-mode~ defaults to =session=; set it to =stateless= to use the older one-shot JSON-decision path. ~agent-chief-interval~ controls the timer interval in seconds. ~agent-chief-directory~ is the working directory for chief sessions and one-shot calls; by default it uses =/Users/pablostafforini/My Drive/Epoch/= when that directory exists, falling back to ~user-emacs-directory~ otherwise. ~agent-chief-session-instance-name~ defaults to =chief= and is used as the instance name for the dedicated interactive session.

~agent-chief-state-file~ is an Org file used as the durable, inspectable state store; =agent-chief= never writes opaque memory. Day plans and manual notes are appended there and, when a chief session is live, submitted into that session as conversational context.

State context treats only a =Plan YYYY-MM-DD= heading dated today as current. Older plan headings are supplied as historical context, not active obligations, unless restated in today's plan.

~agent-chief-record-model-state-updates~ controls whether model-proposed state updates from stateless ticks are appended to the state file. It defaults to nil because periodic model observations are not user-approved durable memory. Use explicit notes and day plans for ordinary state updates.

~agent-chief-context-functions~ is the extension point for agenda, task, calendar, project, or custom status snippets. Each function is called with no arguments and should return a string. Nil and empty strings are ignored. The state file is included separately, truncated to ~agent-chief-state-max-chars~ characters. ~agent-chief-max-turns~ limits Claude Code ticks; Codex ticks use the existing =codex exec= settings from =agent-codex=.

In session mode, ~agent-chief-start-session~ sends only a short conversational kickoff asking the model to ask for today's plan; it does not dump the state file or stateless JSON contract into the visible transcript. Heartbeat prompts ask the model to respond exactly =No nudge.= when no contact is warranted, or =Nudge: MESSAGE= when it should alert the user. The backend's ordinary notification event tells =agent-chief= when the response is complete; =agent-chief= then inspects the session text since the heartbeat and calls ~agent-chief-notify-function~ only for a nudge. The default notification function logs the message and uses =alert.el= when available. ~agent-chief-system-prompt~ is the standing instruction that makes the loop selective and forbids inventing obligations not present in the supplied context.

In stateless mode, backend output may include echoed CLI transcript text before the answer. The chief loop scans that output and uses the last valid JSON object with a =notify= field as the decision, so echoed response-schema examples do not confuse the parser.

The command ~agent-menu~ opens the unified transient menu. It includes shared entries for session switching, waiting-session jumps, handoff, restart, exit, skill execution, Trajectory CR task worktree creation, project audit, backtrace debugging, Slack-message action routing, alert toggles, terminal maintenance, and a separate Prompts section for prompt capture and captured prompt insertion. Backend modules append their own suffixes to the same menu when loaded.

In EAT-backed Claude and Codex session buffers, ~agent-setup-scroll-keys~ makes PageUp and PageDown send terminal mouse-wheel events, matching the TUI scroll path used by the mouse. PageUp and PageDown in other selected buffers retain their normal bindings and never target a visible AI terminal in another window.

The command ~agent-start-or-switch~ is the main entry point. If no sessions exist, it starts a new session through the selected backend. If sessions already exist, it opens the session switcher. Sessions receive stable home-row keys where possible and display backend icons next to their labels.

The command ~agent-run-skill~ discovers skills from every loaded backend that implements skill discovery. It disambiguates same-named skills by backend label, prompts for declared arguments when a skill frontmatter requests them, and dispatches the invocation to the selected backend. Claude and Codex backends scan global and project-local programmatic skill directories, using both ~project-current~ and nearby tool directories as project-root signals, so batch-only skills can be run from this command without being loaded into ordinary interactive agent sessions.

The command ~agent-capture-prompt~ opens a session-specific Org file and appends a new prompt entry. The command ~agent-insert-captured-prompt~ reads pending nonempty entries for the current session, prompts for one with a short body preview in the completion candidate, inserts its text into the backend prompt without submitting it, and removes the selected Org entry from the capture file. With a prefix argument, it includes legacy entries already marked as inserted. When a session still has pending captured prompts, ~agent-exit~, ~agent-restart~, and ~agent-handoff~ ask for confirmation before closing or replacing that session.

The command ~agent-post-push-ci~ runs the ~post-push-ci~ skill through the
selected backend with =--no-push --commit HEAD=. Use it after a push has
already happened and you want an agent to inspect GitHub Actions failures, fix
the root cause, and continue the authorized CI closeout loop.

The command ~agent-trajectory-new-task~ creates a Trajectory =reasoning-tasks=
task worktree from =origin/main= at =~/Trajectory/reasoning-tasks/<slug>=,
checks out branch =pablo/<slug>=, wires the worktree's =.claude/.env= symlink to the canonical
Rubric Studio key, sparse-checks out the worktree to =.claude=, =meta= and
=platform= (keeping the checkout small instead of materializing the whole task
corpus), runs the sync hook script configured by
~agent-trajectory-sync-worktree-script~, and opens the new worktree in Dired.
The sync script is the same SessionStart hook every later session runs, and
the single source of truth for composing the local =AGENTS.md= and =CLAUDE.md=
instruction overlay, linking the canonical key and injecting private skills.
The command is the Emacs equivalent of the shell =newtask= helper, but it does
not depend on the local =main= worktree's current branch.

The commands ~agent-handoff~, ~agent-audit-project~, ~agent-debug-backtrace~, ~agent-act-on-slack-message~, ~agent-exit~, and ~agent-restart~ resolve a backend from the current session buffer or by prompting. This lets the same keybinding operate on Claude or Codex sessions without separate wrapper commands. The old per-backend command names (~agent-claude-handoff~, ~agent-codex-restart~, and so on) remain available as obsolete aliases.

~agent-handoff~ reads the backend's entry in ~agent-handoff-files~, kills the current session buffer, and starts a new session with the handoff prompt. ~agent-handoff-from-emacsclient~ accepts the source buffer name from an =emacsclient= argument, so agent-authored handoff commands can close the requesting session even though Emacs evaluates the form outside that buffer. If the source buffer name is unavailable, handoff closes the single existing session buffer for the handoff directory before starting the replacement session, which avoids the CLI's instance-name prompt in unattended loops.

~agent-restart~ kills the current session buffer and resumes the same session in place, preserving the session's directory, instance name, account, and any launch state the backend's ~:restart-options~ function captures. It prompts when the active account differs from the session account and refuses to restart when a named account is no longer configured or when no resumable session identity exists. ~agent-audit-project~ prompts for a project directory and runs each skill in ~agent-audit-skills~ sequentially through the backend's non-interactive prompt runner. ~agent-debug-backtrace~ saves the current Emacs backtrace, asks =gptel= to identify likely packages, and starts a session in the selected package source directory with instructions to fix the bug. ~agent-setup-kill-on-exit~ arranges for a session buffer to be killed when its process exits, consulting the backend's ~:before-kill-check~ slot first.

~agent-before-exit-functions~ can delay ~agent-exit~ for cleanup work.
Each function receives the resolved backend and session buffer; returning nil
aborts the exit.
Once a forced session close proceeds, Agent kills the target buffer without
running buffer-local kill-query prompts, so stale session buffers do not survive
restart or exit workflows.

Set ~agent-before-exit-skill-name~ (a single skill) or
~agent-before-exit-skill-names~ (an ordered list) to submit interactive skills
before exiting matching sessions. Each entry in ~agent-before-exit-skill-names~
is either a skill-name string or a list whose car is the skill name and whose
cdr is a plist accepting ~:directories~ (restrict where that skill runs,
overriding ~agent-before-exit-skill-directories~) and ~:args~ (a string
appended to the submitted command). For example:

#+begin_src emacs-lisp
(setq agent-before-exit-skill-names
      '("session-learning-capture"
        ("update-log" :directories ("~/My Drive/Epoch") :args "--auto")))
#+end_src

~agent-run-skill-before-exit~ uses each backend's registered skill command
prefix so Claude sessions receive slash commands and Codex sessions receive
dollar-prefixed skill commands, then submits the first applicable skill. The skills run in
order, each submitted after the previous one finishes, and the session exits
after the last; ordinary ready notifications are left unchanged while the chain
runs. When ~agent-before-exit-skill-names~ is nil, ~agent-before-exit-skill-name~
is used as a single-skill fallback. Leave ~agent-before-exit-skill-directories~
nil to run an unscoped skill before exiting every session.
~agent-before-exit-skill-min-duration-seconds~ defaults to 60 seconds, so very
short sessions skip the before-exit skills when the backend can report elapsed
session time.
Set the buffer-local variable ~agent-before-exit-skill-inhibit~ non-nil for
orchestration sessions that must close immediately without running the
configured before-exit skill. Handoff commands set this automatically on the
source session before closing it.

The chain is driven by session stop events and guarded by a watchdog:
if the skills have not finished within ~agent-before-exit-timeout~
seconds (default 600), the chain is abandoned with a warning and the
session is left open instead of being stranded.

Backends can veto that automatic close while the submitted skill invocation is
still visible as unaccepted prompt input. Codex uses this to avoid closing a
session when the dollar-prefixed skill name was inserted but not submitted,
while ignoring submitted command scrollback, visible placeholder text, and
autosuggestion text. The readiness check recognises the standard Codex prompt
markers (=›= and =❯=); a chain that stalls after the first skill usually means
the running Codex renders an unrecognised prompt marker.

Backends can provide an atomic submit operation for before-exit commands.
Claude and Codex both target the resolved session buffer directly, insert the
skill command, and submit it once before the terminal buffer is displayed
again. Codex delegates this to =codex.el='s target-buffer submit helper.

The command ~agent-chief-start-session~ starts or reuses a dedicated Claude Code or Codex session using ~agent-chief-session-instance-name~, sends the chief-of-staff operating contract into the session, asks the model to request today's plan there, and starts the heartbeat timer. The command ~agent-chief-switch-to-session~ jumps back to that session so the user can reply normally.

The command ~agent-chief-start~ starts only the repeating Emacs timer. Without a prefix argument it also schedules an immediate tick; with a prefix argument, it waits ~agent-chief-interval~ seconds before the first tick. ~agent-chief-stop~ cancels the timer. ~agent-chief-tick~ runs one check using ~agent-chief-mode~. ~agent-chief-session-heartbeat~ forces a session-mode heartbeat, while ~agent-chief-stateless-tick~ forces one stateless JSON-decision check.

The command ~agent-chief-open-state~ opens the auditable Org state file. ~agent-chief-add-note~ appends a manual note, and ~agent-chief-set-day-plan~ appends today's plan. When a chief session is active, both commands also submit the new context into that session. These commands are intentionally simple: the durable source of truth remains ordinary text that can be reviewed, edited, and audited outside the model.

** Backend registration and display
:PROPERTIES:
:CUSTOM_ID: h:backend-functions
:END:

#+findex: agent-register-backend
#+findex: agent-start-session
#+findex: agent-backend-icon-string
#+findex: agent-svg-icon
#+findex: agent-display-name
#+findex: agent-parse-skill-frontmatter
#+findex: agent-notify
#+findex: agent-protect-buffer
#+findex: agent-kill-session-buffer
The function ~agent-register-backend~ registers an AI tool by constructing an ~agent-backend~ struct from keyword arguments. Backend modules call it at load time. Keywords are validated against the struct's slot names, and the required slots ~:buffer-p~, ~:find-all-buffers~, and ~:start-session~ are checked so the shared session layer can rely on a consistent interface.

The full slot set is: identity and presentation (~name~, ~label~, ~icon~, ~program~), buffer discovery (~buffer-p~, ~find-all-buffers~, ~find-buffers-for-dir~), session lifecycle (~start-session~, ~session-identity~, ~restart-options~), send primitives (~send-string~, ~send-return~, ~submit~), session state probes (~waiting-p~, ~busy-p~, ~background-tasks-p~, ~duration-ms~, ~display-name-suffix~, ~notify~), accounts (~account-env-var~, ~accounts~, ~account-file~, ~shared-config-items~, ~canonical-home~, ~account-init~), skills (~run-prompt~, ~skill-roots~, ~skill-command-prefix~), integration hooks (~sync-theme~, ~menu-suffixes~), and exit safety (~before-exit-ready-to-close-p~, ~before-kill-check~).

The ~:start-session~ slot starts a new session parameterized by an ~agent-session~ identity struct, optionally with an initial prompt or a resume id. The ~:session-identity~ slot returns a live session buffer's CLI session id, used by ~agent-restart~ to resume in place. ~agent-start-session~ is the core dispatcher that starts a session through its backend's ~:start-session~ function, passing any extra backend-specific options through. The ~:send-string~ slot inserts text into a session's prompt without submitting it, ~:send-return~ submits the pending prompt, and ~:submit~ atomically inserts and submits; the core wrappers ~agent-send-string~, ~agent-send-return~, and ~agent-submit~ dispatch through these slots and emit the corresponding session events.

~agent-display-name~ returns a human-readable label for a session buffer. It starts with the project name, adds an instance name when needed to disambiguate duplicates, and lets backends append their own suffixes. The Claude backend uses this to expose branch identity in the modeline and switcher.

~agent-parse-skill-frontmatter~ reads =SKILL.md= frontmatter shared by Claude and Codex skill runners. It recognizes names, descriptions, argument hints, argument sources, argument choices, defaults, multiplicity, user-invocable flags, and model overrides.

~agent-svg-icon~ renders SVG strings as inline images, using the current face foreground when the SVG uses =currentColor=. Backends use this for modeline and transient display and can fall back to text abbreviations when SVG rendering is unavailable.

** Modeline and status helpers
:PROPERTIES:
:CUSTOM_ID: h:modeline-functions

#+findex: agent-claude-status-cost
#+findex: agent-claude-status-context-percent
#+findex: agent-claude-status-token-count
#+findex: agent-claude-status-duration-ms
#+findex: agent-claude-status-session-usage
#+findex: agent-claude-status-weekly-usage
#+findex: agent-codex-status-model
#+findex: agent-codex-status-effort
#+findex: agent-codex-status-duration-ms
The Claude and Codex status helpers are intended for modeline integrations such as =doom-modeline=. Claude status functions read the current session status JSON and expose model, reasoning effort, cost, context, duration, and token information. Claude usage functions expose account-level utilization returned by the Anthropic usage endpoint. Codex status functions expose the configured model, reasoning effort, and elapsed session duration. When Codex has no explicit reasoning-effort override, the status helper reports Codex's default =medium= effort. The session switcher uses backend busy, input-readiness, and background-work detectors to avoid showing actively responding sessions as waiting, and to distinguish truly idle waiting sessions from sessions that are accepting input while background terminals, agents, or tasks are still running. A session counts as waiting only when it is blocked on the user, meaning it has stopped and will not proceed until the user submits something. Being able to queue text mid-turn is not waiting, since both CLIs accept typed input at any point. Codex app-server sessions learn turn boundaries from the JSON-RPC stream, so an inactive turn on a live app server is authoritative for waiting and an active turn is authoritative for busy, regardless of whether the prompt accepts input. Terminal sessions have no such signal and fall back to the session-event state machine and to scanning rendered status text. Codex prompt submission clears the previous waiting marker at the target buffer, so a session does not remain colored as waiting after the user sends a new prompt.

* Transient menu
:PROPERTIES:
:CUSTOM_ID: h:transient-menu
:END:

#+findex: agent-menu
Backend modules extend ~agent-menu~ through ~transient-append-suffix~ after the core menu is available, first removing their own existing suffixes so reloading does not duplicate or stale-position those entries. The base menu contains shared session, tool, alert, buffer, prompt, and option entries. The Claude module appends branch navigation, batch TODOs, TODO sending, log browsing, status polling, Claude account selection, and branch-kill warnings. The Codex module appends Codex resume/fork commands and Codex account selection. In the Options group, =-c= selects the Claude account and =-x= selects the Codex account so the two account selectors appear next to each other. Both account infixes share one implementation in =agent-account.el=, and both sync the selected account's config home as soon as the selection is made.

Boolean menu infixes use a shared transient class that toggles the bound variable each time it is invoked. The theme-sync infix additionally calls ~agent-sync-theme-now~ when enabling theme sync, so backend configuration files are updated immediately.
