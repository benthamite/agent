This manual describes the features and customization options for the Emacs Lisp package =agent.el=.

* Overview
:PROPERTIES:
:CUSTOM_ID: h:overview
:END:

=agent.el= collects the Emacs integration layer for AI coding command-line tools. It provides a shared session model, a unified transient menu, notification handling, terminal helpers, backend modules for Claude Code and Codex, and an optional chief-of-staff loop.

The package is split into a small backend-agnostic core and focused modules:

| Module               | Role                                                                                                                                                                                                                        |
|----------------------+-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| =agent.el=           | Core: backend registry, session identity and state machine, session keys and teardown, unified orchestration commands (handoff, restart, exit, resume, branch navigation, skills, audits, backtrace debugging), transient menu, alerts, theme sync |
| =agent-account.el=   | Multi-account support shared by all backends: selection, persistence, per-account config homes, symlinked shared state                                                                                                      |
| =agent-capture.el=   | Persisted Org prompt capture, keyed to the session it targets                                                                                                                                                               |
| =agent-project.el=   | Account-scoped project sources: registry and path-pattern candidates, model ranking, and the project prompt for things that carry no directory of their own                                                                 |
| =agent-slack.el=     | Slack-message-to-project routing: reads the message at point as text with no directory of its own, leaving the project to the shared project reader                                                                          |
| =agent-forge.el=     | Forge-notification-to-project routing: starts a session in the working tree of the repository the notification belongs to                                                                                                   |
| =agent-mu4e.el=      | Email-to-project routing: reads the mu4e message at point as a maildir path, leaving the project to the shared project reader                                                                                                |
| =agent-snippet.el=   | Yasnippet TAB expansion and snippet insertion in eat-based session buffers                                                                                                                                                  |
| =agent-todo.el=      | Org TODO workflows that work with any backend: batch processing of a list of entries and routing the entry at point to a session                                                                                             |
| =agent-claude.el=    | Claude Code backend: integrates =claude-code.el= with status and usage polling, hook setup, and ~agent-claude-mode~                                                                                                          |
| =agent-claude-cli.el= | Quarantined undocumented Claude CLI conventions: Keychain credential naming, the usage API endpoint, the =~/.claude/projects/= directory encoding, transcript JSONL parsing, and the =.claude.json= merge engine            |
| =agent-codex.el=     | Codex backend: integrates =codex.el= with theme sync, =codex exec= execution, =config.toml= helpers, modeline helpers, and ~agent-codex-mode~                                                                               |
| =agent-chief.el=     | Inspectable chief-of-staff loop: Emacs owns timers, state, context collection, and notifications, while Claude Code or Codex provides one-shot judgment on each tick                                                        |

The main workflow is to load =agent.el=, require the backend modules you use, and enable their minor modes (see [[#h:minor-modes][Backend minor modes]]); loading a backend module installs nothing by itself. Once the Claude and Codex modules are active, =M-x agent-menu= and =M-x agent-start-or-switch= operate across both tools. Sessions are grouped by account when the backend exposes account metadata, highlighted when waiting for input, and disambiguated by project and instance name when several sessions share a directory.

The package depends on =transient= for menus, =consult= for completion, =claude-code.el= for the Claude backend, and =codex.el= for the Codex backend. All four are declared in the package metadata so that the package manager builds =agent= with them available; the backend modules hard-require their respective backend at load time. Optional integrations use packages such as =yasnippet=, =doom-modeline=, =gptel=, =agent-log=, and =monet= when those are available.

* Architecture
:PROPERTIES:
:CUSTOM_ID: h:architecture
:END:

** Session identity
:PROPERTIES:
:CUSTOM_ID: h:session-identity
:END:

#+findex: agent-session
#+findex: agent-session-buffer-name
Every live session buffer carries a buffer-local ~agent-session~ struct, captured once when the session starts. Its slots are ~backend~ (the backend symbol), ~account~ (the account name, or nil for the default), ~directory~ (the abbreviated project directory), ~instance~ (the instance name, or nil), and ~id~ (the CLI session id, or nil until known). The function ~agent-session~ returns the struct for a buffer, and ~agent-session-buffer-name~ derives the canonical buffer name from the identity. All orchestration code reads identity from this struct; nothing parses buffer names.

#+findex: agent-session-buffers
#+vindex: agent-session-id-functions
The ~id~ slot holds the backend's native session id and is maintained for the whole session lifetime: a non-fork resume seeds it in ~agent-start-session~, the Claude backend records the ~session_id~ reported by every status poll (so a branch switch, which changes the id, updates it), and the Codex backend records the id ~codex-session-identity~ reports on every CLI hook event. A fresh session therefore acquires its id within one status poll interval (Claude) or at its first hook event or prompt submission, whichever comes first (Codex); a fresh app-server Codex session knows its thread id before any CLI hook event fires, so the submission hook is the earliest per-buffer signal. Whenever the recorded id changes, the abnormal hook ~agent-session-id-functions~ runs with the session buffer, so optional integrations — such as the Agent Log bridge — can observe identity without reading private variables. The public surface for such integrations is ~agent-session~, the ~agent-session-id~ accessor, ~agent-session-buffers~ (all live session buffers across backends), and ~agent-session-display-state~.

** Session state machine
:PROPERTIES:
:CUSTOM_ID: h:session-state-machine
:END:

#+findex: agent-session-event
Each session buffer tracks its readiness in the buffer-local variable ~agent--session-state~, which is one of ~unknown~, ~busy~, ~awaiting-input~, or ~closing~. Buffers start as ~unknown~ and stay there until a session event arrives, so a state that was never observed is never presented as one that was; the session switcher renders such sessions with ~agent-unknown~ and ~agent-jump-to-waiting~ skips them. All transitions go through ~agent-session-event~, which accepts the events ~stop~, ~idle-prompt~, ~blocked~, ~submit~, ~activity~, and ~exit-request~. An ~activity~ event marks the session busy on evidence that it is working. It exists because Claude Code publishes no turn-start hook, so turns the user did not type — one driven by remote control, a scheduled task, or a resumed background job — would otherwise be unobservable, leaving the session displayed as waiting while it works. Claude's status line reports a fresh ~prompt_id~ for every turn whatever its origin, and ~agent-claude--read-status~ already polls that file for the modeline, so ~agent-claude--detect-turn-start~ emits ~activity~ when the identifier changes. No extra hook or configuration is needed. Detection latency is one poll interval, ~agent-claude-status-interval~. A turn shorter than that interval both begins and ends between polls, and its ~stop~ event has already landed by the time the change is seen, so that case is detected and skipped rather than stranding the session as busy. A ~blocked~ event marks the session as waiting on the user without firing a ready alert, and is used for permission and elicitation dialogs: Claude reaches those from inside a turn with a tool call still in flight, so nothing else reports them as waiting even though they proceed only once the user answers. Backends translate raw CLI notifications into these events and never set session state directly. A ~stop~ or ~idle-prompt~ event first offers the transition to the before-exit chain; when the chain consumes it, ready alerts and display refreshes are suppressed. Ready alerts fire only for ~idle-prompt~ events, and a ~submit~ event delivered while the session is already busy is ignored, because backend submission hooks can fire more than once per submission.

** Session teardown and leak policy
:PROPERTIES:
:CUSTOM_ID: h:session-teardown
:END:

Session resource cleanup has a single owner: ~agent--session-teardown~ runs a session buffer's ~agent--teardown-functions~ exactly once, whether the buffer is killed first or the CLI process exits first, then releases the session's home-row key. Backends and features register their per-session resources (status poll timers, monet servers, before-exit chains) as teardown functions instead of installing their own kill-buffer hooks. Claude buffers also adopt any already-running Monet server when ~agent-claude-mode~ is enabled or reloaded, so teardown owns sessions that predate the current Agent code. The monet websocket server needs one extra guard: when the Claude client disconnects, ~monet--on-close-server~ drops the session from monet's own table before teardown can look it up, so an =:after= advice closes the listening server at that moment rather than letting it escape to the GC safety net. Resources that escape teardown are not silently reaped: safety nets report each one through a =Warnings= buffer entry tagged =agent=, naming the leaked resource. A leak warning therefore indicates a lifecycle bug worth reporting, not routine noise. The Monet GC sweep identifies servers by ownership, not by process name: Agent registers every server process it sees monet create or adopt, and the sweep only ever reaps registered servers that have lost their monet session. Websocket servers belonging to other packages (atomic-chrome, org-roam-ui) share the generic =websocket server on port N= process name but are invisible to the sweep and can never be reported or killed as monet leaks.

** Account model
:PROPERTIES:
:CUSTOM_ID: h:account-model
:END:

#+findex: agent-account-select
#+findex: agent-account-init
Multi-account state lives in =agent-account.el= and is keyed by backend. Each backend declares an accounts alist mapping account names to per-account configuration homes (~agent-claude-accounts~, ~agent-codex-accounts~), a persisted selection file that survives Emacs restarts (~agent-claude-account-file~, ~agent-codex-account-file~), and the environment variable that points the CLI at the selected home: =CLAUDE_CONFIG_DIR= for Claude Code and =CODEX_HOME= for Codex. Account homes keep credentials separate, while shared state (settings, hooks, skills, sessions, history) is symlinked from the backend's canonical home so it remains available after switching accounts; conflicting account-local files are backed up to timestamped =*.agent-backup-*= siblings first. ~agent-account-select~ persists a choice and syncs the account home, and ~agent-account-init~ prepares or repairs a home. The account infix in ~agent-menu~ always asks which backend to change before it asks for an account; it never silently infers the backend from the buffer where the menu happened to be opened. When the merge engine reads a home's =.claude.json=, a parse failure is retried once after a short delay before warning, since a running CLI rewrites the file frequently and a read can land mid-write. The account a session was started under is recorded in its ~agent-session~ struct, so restart and handoff preserve it even after the global selection changes.

#+findex: agent-account-login
Credentials are part of the account model too. A backend may declare the account-local credentials file inside each home (=auth.json= for Codex) and the CLI arguments of its login flow. ~agent-account-login~ — bound to =L= in ~agent-menu~ — runs that login flow with the selected account's environment, so the credentials always land in the right account home; running the bare CLI login in a terminal would write to the backend's default home instead. The command shows the login output, including the authentication URL, in a dedicated buffer and reports success or failure when the flow finishes. Session starts guard on the same declaration: when an account's credentials file is missing — after the in-session logout command, or when tokens were removed out of band — ~agent-start-session~ refuses to spawn a session that could only fail to authenticate and points at ~agent-account-login~ instead. Backends that do not declare a credentials file (Claude Code stores credentials in the macOS Keychain) are assumed logged in and never blocked.

** Backend minor modes
:PROPERTIES:
:CUSTOM_ID: h:minor-modes
:END:

#+findex: agent-claude-mode
#+findex: agent-codex-mode
The global minor modes ~agent-claude-mode~ and ~agent-codex-mode~ own every hook, advice, timer, and notification handler their backend installs. Loading =agent-claude.el= or =agent-codex.el= installs nothing; the modes must be enabled explicitly. Disabling a mode removes its hooks and advice symmetrically and restores the backend's previous notification function, leaving running sessions untouched. A typical setup:

#+begin_src emacs-lisp
(use-package agent
  :config
  (require 'agent-claude)
  (require 'agent-codex)
  (require 'agent-chief)
  (agent-claude-mode 1)
  (agent-codex-mode 1))
#+end_src

** Shared session behavior
:PROPERTIES:
:CUSTOM_ID: h:shared-session-options
:END:

#+vindex: agent-protect-buffers
#+vindex: agent-warn-kill-with-branches
#+vindex: agent-branch-worktree-directory
#+vindex: agent-alert-on-ready
#+vindex: agent-alert-style
#+vindex: agent-alert-sound
#+vindex: agent-alert-sound-player
#+vindex: agent-backtrace-file
#+vindex: agent-handoff-files
#+vindex: agent-audit-skills
#+vindex: agent-audit-project-directories
#+vindex: agent-debug-backtrace-model
#+vindex: agent-debug-backtrace-backend
#+vindex: agent-prompt-capture-directory
#+vindex: agent-prompt-capture-auto-save-delay
#+vindex: agent-sync-theme
#+vindex: agent-sigwinch-delay
#+vindex: agent-session-annotation-max-width
The user option ~agent-protect-buffers~ is a boolean that defaults to ~t~. When enabled, killing a live AI session buffer prompts for confirmation through ~agent-protect-buffer~. Buffers whose processes have already exited are allowed to die without the prompt.

The user option ~agent-warn-kill-with-branches~ is a boolean that defaults to ~t~. When enabled, killing a session that other sessions were branched from asks a second confirmation naming how many branches it has, after the ordinary kill-protection prompt. The check scans only the sessions that could descend from the one being killed, and any failure to scan allows the kill, so a session never becomes unkillable because its transcripts moved. It replaces ~agent-claude-warn-kill-with-branches~, which is kept as an obsolete alias; that option was declared but never read by any code, so setting it had no effect until the check described here existed.

The user option ~agent-branch-worktree-directory~ names the base directory for the git worktrees ~agent-create-branch~ creates with a prefix argument ([[#h:branch-navigation][Branch navigation]]). It defaults to a location under the cache directory, away from cloud sync, and replaces ~agent-claude-fork-worktree-directory~, which is kept as an obsolete alias. The default path still ends in the literal segment =claude-worktrees=, unchanged from the Claude-only original so that worktrees created before the rename are still found where they were left.

The user option ~agent-alert-on-ready~ is a boolean that defaults to ~nil~. When enabled, backend notification handlers can call ~agent-notify~ to emit visual and/or audible alerts when a session is waiting for input. Codex's own terminal-bell notification path is routed through the same alert setting. ~agent-alert-style~ selects ~visual~, ~sound~, or ~both~; it defaults to ~both~. ~agent-alert-sound~ defaults to ~nil~; set it to a sound file to enable sound alerts. ~agent-alert-sound-player~ optionally names an external sound player when Emacs sound support is unavailable.

The user option ~agent-backtrace-file~ controls where ~agent-save-backtrace~ and ~agent-debug-backtrace~ write Emacs backtraces. It defaults to a file in ~temporary-file-directory~.

The unified orchestration commands share one set of options across backends. ~agent-handoff-files~ maps backend symbols to the handoff files read by ~agent-handoff~. ~agent-audit-skills~ lists the audit skills run by ~agent-audit-project~, and ~agent-audit-project-directories~ stores completion candidates for the audit directory prompt. ~agent-debug-backtrace-model~ and ~agent-debug-backtrace-backend~ configure the =gptel= request used by ~agent-debug-backtrace~ to identify likely culprit packages from an Emacs backtrace.

Slack-message routing has no options of its own any more. The model and =gptel= backend that pick a project from the message are the shared ~agent-project-ranking-model~ and ~agent-project-ranking-backend~ ([[#h:project-options][Project sources]]), and ~agent-act-on-slack-message-model~ and ~agent-act-on-slack-message-backend~ are obsolete aliases of them. The project candidates come from ~agent-project-sources~, so a registry that used to be named by ~agent-epoch-project-registry-file~ now belongs in that alist: that option is obsolete and nothing reads it, which means a configuration setting it alone routes against the default source list instead of the registry. Loading =agent-project= warns when that option still holds a value, because marking a variable obsolete warns only code that mentions it and says nothing to a configuration that merely sets it, which is the whole of what such a configuration does. ~agent-epoch-projects-root~ is an obsolete alias of ~agent-project-registry-root~ and still resolves the registry's relative paths. The function ~agent-epoch-project-candidates~, which read that registry into project plists, is replaced by ~agent-project-candidates~, which reads every source an account has and answers in a different shape. The old name is marked obsolete but no longer defined, so a configuration still calling it is warned at byte-compile time which name replaced it, and fails if it runs. All three renamings are declared in =agent-project.el= ahead of the options they rename, because a setting made before the package loads — which is what ~use-package~'s ~:custom~ does — reaches the new name only while that name is still unbound.

The user option ~agent-prompt-capture-directory~ controls where ~agent-capture-prompt~ stores per-session Org files. Each file is keyed by backend, account, project directory, and session instance, so prompts are linked to the session they target and remain available after Emacs restarts. ~agent-prompt-capture-auto-save-delay~ controls the idle delay before capture buffers are saved automatically.

The user option ~agent-sync-theme~ is a boolean that defaults to ~nil~. When enabled, theme changes in Emacs are persisted through each registered backend's theme-sync handler. This updates configuration files for new or restarted CLI sessions without sending theme commands into active terminal conversations.

The user option ~agent-sigwinch-delay~ is a number of seconds and defaults to =0.5=. It controls how long ~agent-fix-rendering~ waits before sending =SIGWINCH= to a terminal process. Increase it if an AI CLI reads the terminal size before the =eat= window has settled.

The user option ~agent-session-annotation-max-width~ caps the width of session annotations in the session switcher ([[#h:shared-commands][Shared commands]]). It defaults to ~nil~, which applies no cap beyond the fit to the frame. An integer narrows annotations to at most that many columns; it never widens them past what the frame holds, since the frame fit applies either way. Text longer than the resulting width is truncated with an ellipsis. A cap of =0= leaves no room at all, and every session then renders as the bare label it would have without an annotation, rather than a padded label followed by nothing.

Snippet helpers use =yasnippet= and =consult-yasnippet= only when those optional packages are loaded.

** Project sources
:PROPERTIES:
:CUSTOM_ID: h:project-options
:END:

#+vindex: agent-project-sources
#+vindex: agent-project-registry-root
#+vindex: agent-project-ranking-model
#+vindex: agent-project-ranking-backend
#+findex: agent-project-candidates
#+findex: agent-project-read
The =agent-project= module enumerates the projects a session can be started in when the thing the session acts on carries no directory of its own. The user option ~agent-project-sources~ is an alist of (REGEXP . SOURCES). The regexp is searched for anywhere in the account name of the backend that will run the session — anchor it with =\`= and =\'= to match a whole name, since a bare ="epoch"= also matches an account called =epoch-personal= — and the first matching entry wins, so an empty regexp is a catch-all that also covers a backend with no account selected. It defaults to one catch-all entry listing =~/repos/*=.

Each source is either a registry file, whose name ends in =.json=, or a path pattern.

A path pattern may contain wildcards. A wildcard is =*=, =?=, or a =[...]= character class, and a pattern containing one is expanded a single level per wildcard component: =~/repos/*= reaches the children of =~/repos/=, and =~/repos/.worktrees/*/*= its grandchildren two levels down. Wildcard expansion keeps only git repositories and worktrees; a worktree records its git directory in a file rather than a directory, and both count. A pattern without a wildcard names exactly one directory, which is kept whether or not it is a repository, and dropped when it does not exist or is not a directory. A pattern that cannot be expanded at all, such as one holding an unbalanced =[=, is reported in the echo area and skipped, so one malformed source never suppresses the candidates of the others.

A registry is a JSON file holding a =projects= array, in the format the obsolete ~agent-epoch-project-registry-file~ used to read ([[#h:shared-session-options][Shared session behavior]]). Every entry becomes one candidate, labelled by its =id= and =title=, or by its =id= alone when it records no title. Unlike a path pattern it carries a description: the entry's =summary=, or its =aliases= when it records no summary, followed by its =browser_keywords= and its Slack channels; an entry recording none of the four has no description at all rather than an empty one. The keywords are worth their length: they are the terms the project is recognized by elsewhere, repository slugs and domain names among them, which is what a routed Slack message or email is likeliest to name, whereas aliases are often the title restated. An entry that records a JSON =null= where a string belongs counts as recording nothing, so a null summary falls back to the aliases just as an omitted one does. Later stages use that text to judge which project a piece of text is about. An entry's directory is its first =project_doc_paths= folder when it records one, because that folder holds the project's instruction files, its first =repo_paths= directory when it records only that, and the registry root itself when it records neither. The user option ~agent-project-registry-root~ names the directory those relative paths are expanded against; it defaults to ~nil~, and a registry recording relative paths is unusable until it is set. A source naming a registry that does not exist raises an error rather than being skipped, since it points at a file the user meant to have.

The function ~agent-project-candidates~ returns the candidates for an account as plists with ~:label~, ~:directory~, ~:repository~ and ~:description~. The repository is the candidate's local clone: the directory itself for a path source that is a git repository or worktree, the first =repo_paths= directory for a registry entry, and nil for a project holding no clone of its own. It is what ~agent-project-repository-directory~ answers from, which returns the clone of a named repository for an account, or nil when no source holds one that exists. Forge routing asks it for a repository whose worktree Forge does not know or no longer knows, which is what a repository that moved looks like ([[#h:shared-commands][Shared commands]]). Candidates are deduplicated by true path, so listing the same directory twice under different names, or through a symbolic link, yields one entry. A label shared by two candidates is replaced with the abbreviated directory, which is what then appears in completion, so no two projects offer the same string.

The function ~agent-project-read~ asks for one of those candidates. It takes the account, the text of the thing being routed, the completion prompt and a callback, and calls the callback with the directory of the project chosen. It answers through the callback even when nothing is ranked, so every caller reads the answer the same way: the directory arrives in the callback, never as a return value. An account whose sources contribute no candidate at all raises an error rather than offering an empty prompt.

The candidates are ordered by a model before completion only when there is something to order them by: the routed text must hold more than whitespace, and at least one candidate must carry a description holding more than whitespace. A blank string counts as no text on either side, so candidates that came from path patterns alone, or from registry entries whose summary, aliases, keywords and Slack channels are all empty, go straight to completion and cost no request. An empty summary alone is not enough: the keywords and channels are appended to it, so an entry recording a blank summary and one keyword still carries text and is still ranked. When the request is made, ~agent-project-ranking-model~ and ~agent-project-ranking-backend~ name the model and the =gptel= backend it runs on; they default to ~gemini-flash-lite-latest~ on the ="Gemini"= backend, and ranking requires =gptel=, which is otherwise an optional dependency. The model is asked for the candidate labels, comma separated, most likely first. A name it returns is matched to the label it equals, and failing that to the shortest label it starts, so a name the model shortened still finds its project while a label that is itself the start of another still names its own. The candidates it names move to the front of the completion list in the order it gave them, each appearing once however often it is named, and the rest keep their original order behind them, so an answer that names only some projects, repeats one, or invents a label never hides a project. A request that fails is reported in the echo area and leaves the original order standing, so a ranking failure costs order rather than the whole action.

** Org TODO workflows
:PROPERTIES:
:CUSTOM_ID: h:todo-options
:END:

#+vindex: agent-todo-log-directory
#+vindex: agent-todo-in-progress-keyword
The =agent-todo= module has two options, both formerly named after Claude. ~agent-todo-log-directory~ names the directory under which ~agent-batch-todos~ writes one timestamped run directory per batch, holding the raw backend output for each entry; it replaces ~agent-claude-log-directory~. ~agent-todo-in-progress-keyword~ is the Org TODO keyword ~agent-send-todo-at-point~ moves a heading to once it has been sent, and it replaces ~agent-claude-org-todo-in-progress-keyword~. Both old names remain as obsolete aliases. The keyword defaults to ~nil~, which leaves the TODO state alone, because Org ships with only TODO and DONE and has no intermediate state to move to; set it to whichever in-progress keyword your own ~org-todo-keywords~ declares.

** Claude Code backend
:PROPERTIES:
:CUSTOM_ID: h:claude-options
:END:

#+vindex: agent-claude-status-interval
#+vindex: agent-claude-usage-interval
#+vindex: agent-claude-usage-max-interval
#+vindex: agent-claude-accounts
#+vindex: agent-claude-account-file
#+vindex: agent-claude-settings-file
#+vindex: agent-claude-hook-wrapper
#+vindex: agent-claude-statusline-script
#+vindex: agent-claude-status-directory
#+vindex: agent-claude-batch-allowed-tools
#+vindex: agent-claude-batch-permission-mode
#+vindex: agent-claude-batch-max-turns
#+vindex: agent-claude-batch-system-prompt
#+vindex: agent-claude-batch-model
The Claude backend options control account selection, session metadata, and non-interactive execution. ~agent-claude-accounts~ is an alist of account names to Claude configuration directories, and ~agent-claude-account-file~ stores the selected account across Emacs sessions. Use ~agent-claude-select-account~ or the shared account infix in ~agent-menu~ to switch accounts before starting a new session. Both commands are thin wrappers around ~agent-account-select~, which persists the choice and syncs the account's config home; ~agent-account-init~ prepares or repairs any backend's account home.

Status and usage polling are controlled by integer intervals. ~agent-claude-status-interval~ defaults to =5= seconds and reads status JSON emitted by the bundled statusline script. ~agent-claude-usage-interval~ defaults to =300= seconds and backs off up to ~agent-claude-usage-max-interval~, which defaults to =900= seconds. Usage polling reads the account's OAuth token from the macOS Keychain, so accounts authenticated with an API key rather than an OAuth subscription—whose OAuth Keychain store is an empty JSON object—are silently skipped rather than treated as a broken lookup. The Keychain lookup runs from the temporary-file directory, so a poll that fires while the current buffer's =default-directory= names a deleted worktree cannot break the subprocess spawn.

Batch execution options are passed to =claude -p=. ~agent-claude-batch-permission-mode~ defaults to ="auto"=, ~agent-claude-batch-max-turns~ defaults to =30=, and the allowed tool, model, and appended-system-prompt options let you narrow or expand what non-interactive Claude tasks may do.

Four options that used to live here now belong to the backend-agnostic layer, because the workflows they configure work with either backend: ~agent-claude-warn-kill-with-branches~ is now ~agent-warn-kill-with-branches~ and ~agent-claude-fork-worktree-directory~ is now ~agent-branch-worktree-directory~ ([[#h:shared-session-options][Shared session behavior]]), while ~agent-claude-log-directory~ is now ~agent-todo-log-directory~ and ~agent-claude-org-todo-in-progress-keyword~ is now ~agent-todo-in-progress-keyword~ ([[#h:todo-options][Org TODO workflows]]). Each old name remains as an obsolete alias, so an existing configuration keeps working and reports the new name.

The optional =agent-chief= module runs a periodic, auditable chief-of-staff workflow. Emacs owns the schedule, explicit state, and notifications. In the default =session= mode, the selected backend is an ordinary long-lived Claude Code or Codex session that receives heartbeat prompts and remains available for normal conversation.

~agent-chief-backend~ selects =codex= or =claude-code=. ~agent-chief-mode~ defaults to =session=; set it to =stateless= to use the older one-shot JSON-decision path. ~agent-chief-interval~ controls the timer interval in seconds. ~agent-chief-directory~ is the working directory for chief sessions and one-shot calls; by default it uses =/Users/pablostafforini/My Drive/Epoch/= when that directory exists, falling back to ~user-emacs-directory~ otherwise. ~agent-chief-session-instance-name~ defaults to =chief= and is used as the instance name for the dedicated interactive session.

~agent-chief-state-file~ is an Org file used as the durable, inspectable state store; =agent-chief= never writes opaque memory. Day plans and manual notes are appended there and, when a chief session is live, submitted into that session as conversational context.

State context treats only a =Plan YYYY-MM-DD= heading dated today as current. Older plan headings are supplied as historical context, not active obligations, unless restated in today's plan.

~agent-chief-record-model-state-updates~ controls whether model-proposed state updates from stateless ticks are appended to the state file. It defaults to nil because periodic model observations are not user-approved durable memory. Use explicit notes and day plans for ordinary state updates.

~agent-chief-context-functions~ is the extension point for agenda, task, calendar, project, or custom status snippets. Each function is called with no arguments and should return a string. Nil and empty strings are ignored. The state file is included separately, truncated to ~agent-chief-state-max-chars~ characters. ~agent-chief-max-turns~ limits Claude Code ticks; Codex ticks use the existing =codex exec= settings from =agent-codex=.

In session mode, ~agent-chief-start-session~ sends only a short conversational kickoff asking the model to ask for today's plan; it does not dump the state file or stateless JSON contract into the visible transcript. Heartbeat prompts ask the model to respond exactly =No nudge.= when no contact is warranted, or =Nudge: MESSAGE= when it should alert the user. The backend's ordinary notification event tells =agent-chief= when the response is complete; =agent-chief= then inspects the session text since the heartbeat and calls ~agent-chief-notify-function~ only for a nudge. The default notification function logs the message and uses =alert.el= when available. ~agent-chief-system-prompt~ is the standing instruction that makes the loop selective and forbids inventing obligations not present in the supplied context.

In stateless mode, backend output may include echoed CLI transcript text before the answer. The chief loop scans that output and uses the last valid JSON object with a =notify= field as the decision, so echoed response-schema examples do not confuse the parser.

#+vindex: agent-session-annotation-functions
Sessions can also carry a one-line annotation after their name, shown dimmed in the ~agent-session-annotation~ face. The text comes from ~agent-session-annotation-functions~, an abnormal hook: each function is called with a session buffer and returns a string, or ~nil~ to leave the session to the functions after it. The first non-nil answer is the one shown, and the functions after it are not called. =agent= renders whatever it returns and knows nothing about where the text comes from. Whitespace in the answer is collapsed to single spaces, so a multi-line answer cannot break the menu's layout, and an answer that is blank or not a string counts as no annotation. Sessions without an annotation — including sessions every function declines to annotate — render exactly as they did before annotations existed. The default is ~nil~, which shows session names alone; Agent Log adds a function that supplies each session's stored one-line summary ([[https://github.com/benthamite/agent-log][agent-log]]), and with no such integration loaded the switcher looks unchanged. Because this is a hook, an integration adds itself with ~add-hook~ rather than taking a slot over: a function you installed yourself keeps working whichever loads first, and ~remove-hook~ takes either one back out.

Annotations line up in one column across every account group: the labels of annotated sessions are padded to the widest of those labels, measured in display columns, so a name containing double-width characters does not push its annotation to the right. Sessions without an annotation are left unpadded.

#+vindex: agent-session-annotation-max-width
Annotations are truncated with an ellipsis to fit the switcher window, which is as wide as the frame. The fit subtracts everything the line spends around the annotation: the columns to the left of the Sessions column, the key and the padding transient formats a suffix with, the padded label, one separator column, and a two-column right margin. A frame too narrow for that budget yields a short annotation rather than none, since the fit never drops below twenty columns. Setting ~agent-session-annotation-max-width~ to an integer caps the result ([[#h:shared-session-options][Shared session behavior]]); it can only narrow an annotation, never widen it past what the frame holds. A cap that leaves no room — that is, =0= — renders the bare label instead.

A function added to ~agent-session-annotation-functions~ must be cheap and free of side effects: building the switcher calls it more than once per session, because aligning the annotations needs every label's width before any label is final. Reading a value from memory is appropriate; reading a file or contacting a process is not.

The command ~agent-act-on-slack-message~, called on a message in a Slack room
buffer, starts a session in the project that message is about and inserts its
permalink into the prompt without submitting it. With a prefix argument it
inserts the permalink into a running session instead. Its extractor,
~agent-slack-context~, answers with the message text and no directory, since a
message names no project of its own: the project is read from the account's
sources and ranked by that text ([[#h:project-options][Project sources]]).

The command ~agent-act-on-forge-notification~ is the Forge counterpart of
~agent-act-on-slack-message~. Called on a notification in
~forge-list-notifications~, it starts a session in the working tree of the
repository that notification belongs to and inserts the issue or pull request
URL into the prompt without submitting it. It also accepts the topic at point,
so it works from a topic buffer or a Magit status buffer, and with a prefix
argument it sends the URL to a running session instead of starting one. Not
every notification is about a topic: Github also notifies about check suites,
commits and releases, and Forge records no topic for those. Such a notification
is routed as itself, because it names a repository to work in and a URL to
read; its title goes into the prompt with the URL, since the URL of a failed
workflow run names the page listing every run of the repository and the title
is what says which one this is. The
command is a thin wrapper over the routing layer described below: its
extractor, ~agent-forge-context~, reads the subject at point and answers with a
context anchored in the working tree, so the project reader is usually never
consulted.

A Slack message has to be classified to find its project, whereas a Forge
notification already records its repository. Where that repository is cloned is
a second question, and it is asked in three steps. Forge answers first, from the
worktree it recorded; it records one only for a repository it has seen from a
local clone, and it forgets one whose path stopped being a worktree, which is
what moving a repository does to every path at once. The account's project
sources answer next, with ~agent-project-repository-directory~: they are where
the clones live, so they know the current path of a repository that moved and
the path of one Forge never saw. When neither knows, the context carries no
directory and the core reads a project from its text, which leads with the
repository's slug so that ranking puts the right project first. Nothing is
refused for want of a clone.

The command ~agent-act-on-email~, called on a message in a mu4e headers or
view buffer, starts a session in the project that message is about and inserts
the message's maildir path into the prompt without submitting it. With a
prefix argument it sends the path to a running session instead. The payload is
the path rather than the text of the mail because an agent can open that file
itself and read the headers, the body and any attachments from it, which no
excerpt pasted into a prompt would carry. Like Slack routing and unlike Forge
routing, the context names no directory: a message belongs to no project of its
own, so its extractor, ~agent-mu4e-context~, answers with the subject and the
sender as the text the project is ranked against ([[#h:project-options][Project sources]]).

The sender comes from the message's =:from= field, which =mu= returns as a
list of =(:email EMAIL :name NAME)= plists — one per sender, with the name
absent when the sender gave none — and reads as =Name <address>=, or as the
bare address when there is no name. Like its Slack and Forge counterparts, the
command loads its foreign package itself and says so when it is missing, since
the command is autoloaded and can therefore be called from a buffer that has
never loaded mu4e.

It signals an error when the message records no path — mu4e reports a missing
string field as the empty string rather than as nil, so an empty path counts as
no path — and when the recorded file cannot be read. A maildir file name
encodes the message's flags, so reading a message, or another mail program
touching it, renames the file, and mu's index can name a path that no longer
exists until it is reindexed. As with a stale Forge clone path, that is an
ordinary failure, and catching it here is better than handing the agent a path
it cannot open.

#+findex: agent-act-on-thing-at-point
#+vindex: agent-at-point-things
The menu binds no routing command directly. ~agent-act-on-thing-at-point~, bound to =.= in the Tools column, walks ~agent-at-point-things~ and runs the extractor of the first entry whose predicate matches the current buffer: a backtrace in a =*Backtrace*= buffer, a Slack message in a Slack room buffer, a Forge notification or topic, an email in a mu4e headers or view buffer, or an org TODO heading. Every predicate answers from the buffer alone — the buffer name, the buffer-local variable =slack= sets on room buffers, the major mode, the org TODO state — so dispatch never loads a module to ask whether it applies, and the Forge and mu4e lookups run only in a buffer whose major mode can hold what they look for. A Magit buffer is one of those, and it can be current with =forge= not yet loaded; since forge's lookups are not autoloaded, the Forge predicate also checks that they are defined, and falls through to the next thing rather than failing when they are not. The predicate claims any notification, not only one about a topic, because the extractor routes the notification itself when Forge records no topic for it. The mu4e modes need no such check, because the files that define those modes require the one that defines the lookup. When nothing matches, the command signals an error naming those five kinds, in the order the table holds them.

Recognizing the thing, choosing the session, and delivering the payload are three separate layers. An extractor takes a continuation rather than returning a value, because extraction can require a network round-trip, and calls it with a context plist: =:directory= when the thing carries a working directory, as an absolute path, =:text= when it carries only text to choose a project from, =:payload= for what to send, =:submit= for whether to submit it, and an optional =:after= thunk run once the payload is delivered. Before extraction begins, the core resolves the backend and captures that backend's selected account as one pair. A later account switch cannot change which project sources this invocation reads, which matters for asynchronous extractors such as Slack. A context that names a directory starts its session there; one that does not has its project read from the captured account's sources with ~agent-project-read~, ranked by its text. With a prefix argument the payload goes to a running session chosen by completion instead of a new one, so the same key routes a thing either way.

A running session already has a directory, so on that path the core tells the extractor not to resolve one, and an extractor that has to work for its directory leaves it out. That saves what the work costs: routing a backtrace to a running session asks no model which packages it implicates and prompts for none, and routing a Forge topic there no longer refuses a repository that was never cloned locally. The extractors that carry only text are unaffected, since the project they would otherwise pick is chosen after the session is, and only for a new one.

What each kind sends differs, because the payloads differ. A Slack permalink, a Forge topic URL and an email's maildir path are references to something the agent should read, so they arrive unsubmitted and you type the request next to them. A backtrace and an org TODO already are the request, so they submit.

A payload marked =:submit= reaches a *new* session as its initial prompt, handed to the backend at launch rather than typed into the terminal afterwards. Claude passes it on the CLI's command line, and Codex does too except when it is resuming a session or running through its app server, where it sends the prompt itself once the session is up. Either way the payload never races the terminal: nothing sequences typed input against a session whose process has only just been spawned, and these sessions often start in a directory the CLI has never opened, where it greets the user with a trust prompt that the typed text would answer instead of the model. A payload the context does not submit is typed in on both paths, since it is meant to sit in the prompt for the user to edit. A submitted payload reaching an already-running session is typed in and then submitted, because that session is past its startup and needs no hand-off at launch.

Because extraction can be asynchronous, the continuation may run long after the command was invoked, in whatever buffer the user has moved to since. The dispatcher therefore captures the invocation buffer and resolves the backend up front, before the extractor runs: the session adopts the backend of the buffer the thing was read from rather than of wherever the callback lands, no backend prompt appears in the middle of an asynchronous wait, and the =:after= thunk runs back in the invocation buffer, which starting a session has displaced as the current one. A thunk whose buffer has been killed meanwhile is dropped, since the thing it would act on is gone.

The commands ~agent-handoff~, ~agent-audit-project~, ~agent-debug-backtrace~, ~agent-act-on-slack-message~, ~agent-exit~, and ~agent-restart~ resolve a backend from the current session buffer or by prompting. This lets the same keybinding operate on Claude or Codex sessions without separate wrapper commands. The old per-backend command names (~agent-claude-handoff~, ~agent-codex-restart~, and so on) remain available as obsolete aliases.

~agent-handoff~ reads the backend's entry in ~agent-handoff-files~, kills the current session buffer, and starts a new session with the handoff prompt. ~agent-handoff-from-emacsclient~ accepts the source buffer name from an =emacsclient= argument, so agent-authored handoff commands can close the requesting session even though Emacs evaluates the form outside that buffer. If the source buffer name is unavailable, handoff closes the single existing session buffer for the handoff directory before starting the replacement session, which avoids the CLI's instance-name prompt in unattended loops.

~agent-restart~ kills the current session buffer and resumes the same session in place, preserving the session's directory, instance name, account, and any launch state the backend's ~:restart-options~ function captures. It prompts when the active account differs from the session account, and it leaves the account unset when neither the session nor the global selection names one, so a session that ran under the backend's ambient default home is restarted there rather than pushed onto an account it never used.  Every precondition is checked before the old session is killed: restart refuses when a named account is no longer configured, when the account is logged out, or when no resumable session identity exists, and in each case the running session survives untouched. ~agent-audit-project~ prompts for a project directory and runs each skill in ~agent-audit-skills~ sequentially through the backend's non-interactive prompt runner. ~agent-debug-backtrace~ saves the current Emacs backtrace, asks =gptel= to identify likely packages, and submits instructions to fix the bug to a session started in the selected package source directory, or to a running session under a prefix argument. Its extractor, ~agent--backtrace-context~, schedules the identification to run after the current command rather than doing it inline, because saving the backtrace kills the =*Backtrace*= buffer, which exits the debugger's recursive edit and unwinds the calling frame. ~agent-setup-kill-on-exit~ arranges for a session buffer to be killed when its process exits, consulting the backend's ~:before-kill-check~ slot first. It is not a menu entry: each backend installs it, along with ~agent-disable-scrollback-truncation~ and, for Codex, ~agent-fix-rendering~, from its session-start hook, so the menu carries no buffer-maintenance commands.

~agent-before-exit-functions~ can delay ~agent-exit~ for cleanup work.
Each function receives the resolved backend and session buffer; returning nil
aborts the exit.
Once a forced session close proceeds, Agent kills the target buffer without
running buffer-local kill-query prompts, so stale session buffers do not survive
restart or exit workflows.

Set ~agent-before-exit-skill-name~ (a single skill) or
~agent-before-exit-skill-names~ (an ordered list) to submit interactive skills
before exiting matching sessions. Each entry in ~agent-before-exit-skill-names~
is either a skill-name string or a list whose car is the skill name and whose
cdr is a plist accepting ~:directories~ (restrict where that skill runs,
overriding ~agent-before-exit-skill-directories~) and ~:args~ (a string
appended to the submitted command). For example:

#+begin_src emacs-lisp
(setq agent-before-exit-skill-names
      '("session-learning-capture"
        ("update-log" :directories ("~/My Drive/Epoch") :args "--auto")))
#+end_src

~agent-run-skill-before-exit~ uses each backend's registered skill command
prefix so Claude sessions receive slash commands and Codex sessions receive
dollar-prefixed skill commands, then submits the first applicable skill. The skills run in
order, each submitted after the previous one finishes, and the session exits
after the last; ordinary ready notifications are left unchanged while the chain
runs. When ~agent-before-exit-skill-names~ is nil, ~agent-before-exit-skill-name~
is used as a single-skill fallback. Leave ~agent-before-exit-skill-directories~
nil to run an unscoped skill before exiting every session.
~agent-before-exit-skill-min-duration-seconds~ defaults to 60 seconds, so very
short sessions skip the before-exit skills when the backend can report elapsed
session time.
Set the buffer-local variable ~agent-before-exit-skill-inhibit~ non-nil for
orchestration sessions that must close immediately without running the
configured before-exit skill. Handoff commands set this automatically on the
source session before closing it.

The chain is driven by session stop events and guarded by a watchdog. Each
submitted skill gets up to ~agent-before-exit-timeout~ seconds (default 600) to
finish; the watchdog restarts when the next skill begins. If the current skill
exceeds that interval, the chain is abandoned with a warning and the session is
left open instead of being stranded.

Backends can veto that automatic close while the submitted skill invocation is
still visible as unaccepted prompt input. Codex uses this to avoid closing a
session when the dollar-prefixed skill name was inserted but not submitted,
while ignoring submitted command scrollback, visible placeholder text, and
autosuggestion text. The readiness check recognises the standard Codex prompt
markers (=›= and =❯=); a chain that stalls after the first skill usually means
the running Codex renders an unrecognised prompt marker.

Backends can provide an atomic submit operation for before-exit commands.
Claude and Codex both target the resolved session buffer directly, insert the
skill command, and submit it once before the terminal buffer is displayed
again. Codex delegates this to =codex.el='s target-buffer submit helper.

** Branch navigation
:PROPERTIES:
:CUSTOM_ID: h:branch-navigation
:END:

#+findex: agent-resume
#+findex: agent-create-branch
#+findex: agent-switch-branch
A branch is a session forked from another one: it starts with the parent's whole conversation and then diverges. Branching lets you try a different approach without losing the state you built up, and the three commands here work the same way whichever backend the session belongs to.

~agent-create-branch~, bound to =N=, forks the session in the current buffer and opens the fork in its own buffer under an instance name derived from the time of the fork. By default the branch shares the parent's working tree, which is what starting a second session in the same project would give you. With a prefix argument it also creates a git worktree on a fresh branch under ~agent-branch-worktree-directory~ and runs the fork there, so that destructive git operations in one branch cannot disturb the other. The worktree starts at the parent's HEAD, so uncommitted parent changes are not carried into it; use the isolated form when concurrent git work across branches is a real concern, and the default otherwise. Before the fork starts, the backend's ~:prepare-fork~ slot makes the parent session visible from the new directory, which is what a backend that stores its transcripts per project directory needs in order to resume a session recorded elsewhere.

~agent-switch-branch~, bound to =B=, shows every session sharing a fork ancestor with the current one as an indented tree, each entry carrying its first prompt and its timestamp and the session you are in marked with an asterisk, and switches to the selected session: to its live buffer when it still has one, and otherwise by resuming it in a new buffer. It reports that there is nothing to navigate when the current session has no relatives.

~agent-resume~, bound to =R=, resumes a past session of the current backend, or of a backend it asks for when no session buffer names one, and passes its prefix argument through to the backend, where it means the most recent session.

Both backends supply the lineage these commands read, through the ~:session-headers~ slot, and each derives it from what its CLI already records. Claude Code writes one transcript per session inside a per-project directory, so the scan reads the first line of each transcript in the project the current session belongs to. Codex writes one rollout file per session, all under a single sessions directory, so the scan reads the ~session_meta~ record opening each rollout, keeps the ones whose recorded working directory matches, and takes the parent from ~forked_from_id~. Because that directory holds every Codex session on the machine, the scan is bounded by a start timestamp when the caller only needs one session's descendants.

Codex records subagent threads with the same ~forked_from_id~ field, and those are deliberately left out of the tree. They are forks as far as the file format is concerned, but they are not branches of your conversation: they are threads the model spawned to do work on its own, and offering to switch into one would be offering something a user never chose to create.

** Org TODO commands
:PROPERTIES:
:CUSTOM_ID: h:todo-commands
:END:

#+findex: agent-batch-todos
#+findex: agent-send-todo-at-point
The =agent-todo= module turns Org TODO entries into work for an AI session, and both of its commands work with either backend.

~agent-send-todo-at-point~ formats the heading and body of the TODO at point as a prompt and submits it to a session started for it; it is not a menu entry of its own, since the menu reaches the same routing through ~agent-act-on-thing-at-point~. With a prefix argument it submits the prompt to a running session chosen by completion. Like a Slack message, a TODO names no directory, so the project is read from the account's sources and ranked by the TODO's own text ([[#h:project-options][Project sources]]). It no longer looks for the session belonging to the current file's project: an Org file of tasks rarely sits in the repository those tasks are about. When ~agent-todo-in-progress-keyword~ is set, the heading moves to that keyword once the prompt has been delivered. The heading is remembered as a marker, so the move lands on the heading the prompt came from however far point has travelled while the project was being chosen. A heading deleted in the meantime is left alone: the state change happens after the session exists but before it is shown, so an error there would leave a running session unshown.

~agent-batch-todos~, bound to =b=, collects several TODO entries and runs them one after another without an interactive session. It infers its scope by itself — the region when one is active, the subtree when the buffer is narrowed, and the whole buffer otherwise — then asks for a working directory, and confirms the number of entries before starting unless you selected them as a region, where the selection is confirmation enough. Each entry runs through the resolved backend's ~:exec-prompt~ slot, its raw output is written to a numbered file under a timestamped directory in ~agent-todo-log-directory~, and a summary buffer collects every entry's status, duration, cost, and output when the queue is empty.

Cost appears per entry only for backends whose CLI reports it. Claude's non-interactive runs report a dollar figure and it is shown; =codex exec= reports none, so Codex entries render an em dash in place of a cost and contribute nothing to the total.

** Backend registration and display
:PROPERTIES:
:CUSTOM_ID: h:backend-functions
:END:

#+findex: agent-register-backend
#+findex: agent-start-session
#+findex: agent-backend-icon-string
#+findex: agent-svg-icon
#+findex: agent-display-name
#+findex: agent-parse-skill-frontmatter
#+findex: agent-notify
#+findex: agent-protect-buffer
#+findex: agent-kill-session-buffer
The function ~agent-register-backend~ registers an AI tool by constructing an ~agent-backend~ struct from keyword arguments. Backend modules call it at load time. Keywords are validated against the struct's slot names, and the required slots ~:buffer-p~, ~:find-all-buffers~, and ~:start-session~ are checked so the shared session layer can rely on a consistent interface.

The full slot set is: identity and presentation (~name~, ~label~, ~icon~, ~program~), buffer discovery (~buffer-p~, ~find-all-buffers~, ~find-buffers-for-dir~), session lifecycle (~start-session~, ~session-identity~, ~restart-options~), send primitives (~send-string~, ~send-return~, ~submit~), session state probes (~waiting-p~, ~busy-p~, ~background-tasks-p~, ~duration-ms~, ~display-name-suffix~, ~notify~), accounts (~account-env-var~, ~accounts~, ~account-file~, ~shared-config-items~, ~canonical-home~, ~account-init~), skills (~run-prompt~, ~exec-prompt~, ~skill-roots~, ~skill-command-prefix~), session history (~session-headers~, ~session-prompt~, ~resume~, ~prepare-fork~), integration hooks (~sync-theme~), and exit safety (~before-exit-ready-to-close-p~, ~before-kill-check~).

The ~:start-session~ slot starts a new session parameterized by an ~agent-session~ identity struct, optionally with an initial prompt or a resume id. The ~:session-identity~ slot returns a live session buffer's CLI session id, used by ~agent-restart~ to resume in place. ~agent-start-session~ is the core dispatcher that starts a session through its backend's ~:start-session~ function, passing any extra backend-specific options through. The ~:send-string~ slot inserts text into a session's prompt without submitting it, ~:send-return~ submits the pending prompt, and ~:submit~ atomically inserts and submits; the core wrappers ~agent-send-string~, ~agent-send-return~, and ~agent-submit~ dispatch through these slots and emit the corresponding session events.

The slots that carry the unified session commands are all optional, and a backend that omits one simply does not support the commands dispatching on it. ~:resume~ resumes a past session, receiving the command's prefix argument, and backs ~agent-resume~. ~:session-headers~ returns a hash table mapping session id to a plist of ~:session-id~, ~:forked-from~ and ~:timestamp~, called with a session buffer and optionally with the one session whose descendants the caller cares about, so a backend that keeps every session in one directory can bound its scan; ~:session-prompt~ enriches one such header with the session's ~:first-prompt~. Together they back ~agent-switch-branch~ and the branch check before a kill. ~:prepare-fork~ makes a session recorded under one directory visible from another, which is what lets an isolated branch run in a fresh worktree. ~:exec-prompt~ runs a prompt non-interactively and calls back with a plist of ~:exit-code~, ~:duration~, ~:text~ and ~:raw~; ~agent-batch-todos~ runs through it.

~agent-display-name~ returns a human-readable label for a session buffer. It starts with the project name, adds an instance name when needed to disambiguate duplicates, and lets backends append their own suffixes. The Claude backend uses this to expose branch identity in the modeline and switcher.

~agent-parse-skill-frontmatter~ reads =SKILL.md= frontmatter shared by Claude and Codex skill runners. It recognizes names, descriptions, argument hints, argument sources, argument choices, defaults, multiplicity, user-invocable flags, and model overrides.

~agent-svg-icon~ renders SVG strings as inline images, using the current face foreground when the SVG uses =currentColor=. Backends use this for modeline and transient display and can fall back to text abbreviations when SVG rendering is unavailable.

** Modeline and status helpers
:PROPERTIES:

#+findex: agent-claude-status-cost
#+findex: agent-claude-status-context-percent
#+findex: agent-claude-status-token-count
#+findex: agent-claude-status-duration-ms
#+findex: agent-claude-status-session-usage
#+findex: agent-claude-status-weekly-usage
#+findex: agent-codex-status-model
#+findex: agent-codex-status-effort

The Claude and Codex status helpers are intended for modeline integrations such as =doom-modeline=. Claude status functions read the current session status JSON and expose model, reasoning effort, cost, context, duration, and token information. Claude usage functions expose account-level utilization returned by the Anthropic usage endpoint. Codex status functions expose the configured model, reasoning effort, and elapsed session duration. When Codex has no explicit reasoning-effort override, the status helper reports Codex's default =medium= effort. The session switcher uses backend busy, input-readiness, and background-work detectors to avoid showing actively responding sessions as waiting, and to distinguish truly idle waiting sessions from sessions that are accepting input while background terminals, agents, or tasks are still running. A session counts as waiting only when it is blocked on the user, meaning it has stopped and will not proceed until the user submits something. Being able to queue text mid-turn is not waiting, since both CLIs accept typed input at any point. Codex app-server sessions learn turn boundaries from the JSON-RPC stream, so an inactive turn on a live app server is authoritative for waiting and an active turn is authoritative for busy, regardless of whether the prompt accepts input. Terminal sessions have no such signal and fall back to the session-event state machine and to scanning rendered status text. Codex prompt submission clears the previous waiting marker at the target buffer, so a session does not remain colored as waiting after the user sends a new prompt.

* Transient menu
:PROPERTIES:
:CUSTOM_ID: h:transient-menu
:END:

#+findex: agent-menu
~agent-menu~ is a single static prefix defined in =agent.el=, laid out in four columns: Sessions, Tools, Prompts, and Options. Nothing in the layout depends on which backends are loaded, because every command in it is backend-agnostic. Each one resolves a backend from the current session buffer, or asks when nothing names one, and then dispatches through that backend's slots, so the same key operates on a Claude session and a Codex session alike. There is no longer any mechanism for a backend module to add entries to the menu, and this is deliberate: a backend contributes an implementation for a slot, and the command that calls that slot lives in =agent.el=.

In the Options group, =-c= selects an account. It acts on the current or prompted backend, while its value shows every registered backend's current account at once, so one entry replaces the per-backend account selectors the menu used to carry. The infix shares its implementation with the per-backend account commands in =agent-account.el=, and syncs the selected account's config home as soon as the selection is made.

Boolean menu infixes use a shared transient class that toggles the bound variable each time it is invoked. The theme-sync infix additionally calls ~agent-sync-theme-now~ when enabling theme sync, so backend configuration files are updated immediately.
